# 미니게임 리플레이 계약

이 문서는 `room-runner`, `cat-stairs`, `cat-merge`의 현재 서버 구현을 설명합니다. 세 게임 모두 인증된 회원에게 서버 시드와 세션을 발급하고, 입력 기록을 재생하여 점수를 계산합니다. 클라이언트가 계산한 점수는 제출 계약에 포함하지 않습니다.

## 규칙 버전 선택과 호환

세 게임은 규칙 1과 2를 함께 지원합니다. 게임 코드는 유지하며 목록·시작 API의 선택 쿼리 `rulesVersion`으로 선택합니다. 생략은 1이고 새 앱은 2를 명시합니다. 지원하지 않는 버전은 400 `MINIGAME_RULES_VERSION_NOT_SUPPORTED`로 반환하며 다른 버전으로 대체하지 않습니다. 새 앱은 목록과 시작 응답의 규칙 버전을 확인하고, 요청한 버전과 다르면 랭킹 플레이를 시작하지 않습니다.

완료 요청은 기존 입력 형식을 유지합니다. 입력 제한과 재생 규칙은 요청의 현재 앱 버전이 아니라 저장된 `minigame_runs.rules_version`으로 결정합니다. 규칙 1 세션·리플레이·해시 형식은 그대로 보존하고, 배포 전에 시작한 규칙 1 세션도 기존 만료 시각까지 제출할 수 있습니다. 완료된 규칙 1 세션의 동일 입력 재전송은 만료 후에도 최초 영수증을 반환합니다.

## 공통 API와 저장

- `GET /api/v1/minigames?rulesVersion=2`: 게임 코드, 이름, 설명, `rulesVersion`을 반환합니다.
- `POST /api/v1/minigames/{gameCode}/runs?rulesVersion=2`: `runId`, `gameCode`, `rulesVersion`, 양의 정수 `seed`, 게임별 `maxTicks`, `expiresAt`을 반환합니다. 세션은 발급 후 30분 동안 새 결과를 제출할 수 있습니다.
- `POST /api/v1/minigames/{gameCode}/runs/{runId}/finish`: 입력을 재생하여 `runId`, 이번 `score`, `bestScore`, `personalBest`, `rank`를 반환합니다.
- `GET /api/v1/minigames/{gameCode}/leaderboard`: 해당 게임의 누적 최고점 상위 50명, `myEntry`, `totalPlayers`를 반환합니다.

세션에는 발급된 `game_code`와 `rules_version`을 고정하고, 최고점은 기존 `(game_code, user_id)`로 구분합니다. 규칙 1과 2에서 얻은 점수를 같은 게임별 최고점과 랭킹에 반영합니다. 기존 기록을 삭제·초기화·환산하지 않으며, 더 높은 점수를 얻었을 때만 점수·달성 시각·달성 당시 규칙 버전 메타데이터를 갱신합니다. 동점에서는 기존 값을 유지합니다. 랭킹 목록·내 기록·상위 인원·참가자 수는 규칙 버전으로 나누지 않습니다. 다른 게임의 세션으로 결과를 제출하면 404를 반환합니다. 랭킹은 미탈퇴 사람 회원만 포함하며, 동점은 공동 순위인 `1, 1, 3`으로 표시합니다. 동점 내부 순서는 최고점 달성 시각, 회원 ID 순입니다. 닉네임은 현재 회원 정보에서 읽고 사본을 저장하지 않습니다.

시작·종료·탈퇴는 같은 회원 행을 잠급니다. 이 잠금은 동시 최초 최고점 생성, 최고점 역행, 탈퇴 직후 게임 기록 재생성을 막습니다. 탈퇴 트랜잭션에서 모든 게임 세션과 최고점을 즉시 삭제합니다.

원본 점프·방향 입력은 DB에 저장하지 않습니다. 완료 후 입력의 SHA-256 digest, 서버 점수와 최초 완료 응답을 저장합니다. 같은 세션에 같은 입력을 재전송하면 만료 후에도 최초 응답을 반환하며, 다른 입력을 보내면 409를 반환합니다. 러너의 기존 digest 형식은 유지합니다.

## 시간과 입력 형식

`ticks`는 일시정지 시간을 제외한 60 Hz 게임 진행 시간입니다. 모든 게임에서 `1 <= ticks <= maxTicks`이고, 서버가 관측한 세션 경과 시간에 2초를 더한 값보다 큰 진행 시간은 거부합니다.

요청에는 `jumpTicks`와 `actions` 중 정확히 하나를 넣습니다. 각 배열의 tick은 오름차순이며 중복되지 않고, `1..ticks` 범위 안에 있어야 합니다. 방향은 대문자로 보냅니다.

러너 요청 예시:

```json
{"ticks":301,"jumpTicks":[180]}
```

계단·합치기 요청 예시:

```json
{"ticks":187,"actions":[{"tick":1,"direction":"LEFT"},{"tick":7,"direction":"LEFT"}]}
```

잘못된 입력 종류, 불가능한 상태 전이, 입력 개수 초과는 `MINIGAME_INVALID_REPLAY`로 거부합니다. 요청 DTO의 필수값·타입·기본 범위 위반은 공통 요청 검증 오류를 따릅니다.

## 루틴 러너: room-runner

두 규칙 모두 최대 18,000 tick과 600번의 점프를 허용합니다. 지상 점프, 장애물 생성·이동·충돌을 정수 물리로 재생합니다. 최초 충돌 tick 또는 18,000 tick 도달 시에만 완료할 수 있습니다. 점수는 `floor(ticks / 6)`입니다.

난수는 `state = (1664525 * state + 1013904223) mod 2^32`를 사용합니다. 장애물마다 너비·높이·다음 생성 간격에 차례로 난수를 소비합니다. 규칙 1의 난수 선택과 물리 규칙은 변경하지 않습니다.

규칙별 정수 물리와 장애물 설정은 다음과 같습니다. `tick`은 세션의 진행 tick이고 `next(n)`은 LCG 상태를 한 번 갱신한 뒤 그 값을 n으로 나눈 나머지입니다. 장애물마다 너비·높이·다음 간격 순으로 각각 한 번 소비합니다.

| 설정 | 규칙 1 | 규칙 2 |
| --- | --- | --- |
| 첫 생성 카운트다운 | 90 tick | 60 tick |
| 점프 초기 속도 / tick당 중력 | 16 / 1 | 15 / 1 |
| 이동 속도 | `6 + min(6, floor(tick / 600))` | `8 + min(8, floor(tick / 300))` |
| 장애물 너비 | `24 + next(3) * 10` | `28 + next(3) * 16` |
| 장애물 높이 | `28 + next(3) * 10` | `40 + min(2, floor(tick / 600)) * 6 + next(3) * 16` |
| 다음 생성 간격 | `75 + next(46)` | `65 - min(23, floor(tick / 240) * 3) + next(31)` |

규칙 2의 이동 속도는 40초에 16에 도달합니다. 장애물 높이는 초기 40/56/72에서 20초 이후 52/68/84로 올라가고, 생성 간격은 65~95 tick에서 최단 42~72 tick으로 줄어듭니다. 지상에서는 입력 즉시 점프하며 추가 재점프 대기 시간은 없습니다. 충돌 판정·tick 처리 순서·최대 시간·점수 계산은 유지합니다.

## 고양이 계단: cat-stairs

두 규칙 모두 최대 7,200 tick과 1,200번의 좌우 입력을 허용합니다. 입력은 `LEFT`, `RIGHT`만 가능하며, 연속 입력 사이에 최소 6 tick이 필요합니다. UI는 이보다 빠른 입력을 무시하고 기록하지 않습니다.

초기 열은 0입니다. 다음 방향을 정할 때 러너와 같은 LCG를 한 번 소비하고, 상위 16비트의 마지막 비트로 좌우를 선택합니다. 현재 열이 -3 이하이면 오른쪽, 3 이상이면 왼쪽으로 강제하되 난수는 계속 소비합니다. 맞는 방향으로 이동한 뒤 다음 방향을 생성합니다.

규칙 1의 초기 제한 시간은 180 tick입니다. 매 tick 시간을 먼저 1 줄이고, 0이면 입력 처리 전에 종료합니다. 따라서 만료 tick의 입력은 기록하지 않습니다. 방향을 맞히면 1점을 얻고 제한 시간을 `max(45, 180 - floor(score / 5) * 6)`으로 다시 설정합니다. 틀린 방향, 시간 만료 또는 7,200 tick 도달 시 완료합니다. 종료 후 tick이나 입력을 덧붙이면 거부합니다.

규칙 2는 초기 제한 시간을 72 tick(1.2초)으로 줄이고, 정답 뒤 제한 시간을 `max(18, 72 - floor(score / 3) * 4)`로 설정합니다. 42계단부터는 18 tick(0.3초)입니다. 열·방향 생성, 최소 입력 간격 6 tick, 최대 7,200 tick·1,200입력, tick 시작 시 타이머 차감과 종료 순서, 정답당 1점은 규칙 1과 같습니다.

## 고양이 합치기: cat-merge

두 규칙 모두 최대 18,000 tick과 2,000번의 유효 이동을 허용합니다. `UP`, `RIGHT`, `DOWN`, `LEFT` 방향으로 4×4 보드를 이동합니다. 같은 타일 두 개를 합칠 때 생성된 타일 값만큼 점수를 얻으며, 한 이동에서 같은 타일을 반복 합치지 않습니다. 2,048을 만든 뒤에도 계속 플레이할 수 있습니다.

규칙 1의 초기 타일 두 개와 이후 각 유효 이동의 새 타일은 같은 LCG로 생성합니다. 첫 난수의 상위 16비트를 빈칸 수로 나눈 나머지로 row-major 빈칸을 고릅니다. 두 번째 난수의 상위 16비트를 10으로 나눈 나머지가 0이면 4, 아니면 2를 생성합니다. LCG의 낮은 비트와 짝수 번 난수 소비 간 상관을 피하기 위해 두 선택 모두 상위 비트를 사용합니다.

보드가 달라지지 않는 이동은 UI에서 기록하지 않으며, 서버에 제출하면 거부합니다. 더 이동할 수 없는 보드에서 추가 입력을 보내도 거부합니다. 막힘, 2,000번 이동 또는 18,000 tick 도달 시 종료하며, 사용자가 중간에 기록 저장을 선택해도 됩니다. 유효 이동이 0번인 수동 종료는 `ticks >= 1`, `actions: []`로 제출합니다.

규칙 2는 다음 사항만 변경합니다.

- 초기 타일은 4개를 순서대로 생성합니다.
- 타일 값은 두 번째 난수의 상위 16비트를 4로 나눈 나머지가 0이면 4, 아니면 2입니다. 4의 등장 확률은 25%입니다.
- 유효 이동 8회마다 일반 타일 하나를 생성한 뒤 추가 타일을 하나 더 생성합니다. 추가 타일도 같은 위치·값 생성 규칙을 사용합니다. 추가 생성 시 빈칸이 없으면 생성을 생략하며 난수를 소비하지 않습니다.
- 변화 없는 입력은 이동 횟수나 추가 타일 주기를 진행시키지 않습니다. 클라이언트는 다음 추가 타일까지 남은 유효 이동 수를 표시합니다.

4×4 보드, 장애칸 없음, 합쳐진 값만 점수에 더하는 방식, 중복 합치기 방지, 최대 2,000회·18,000 tick, 수동 종료와 2,048 이후 계속 플레이는 규칙 1과 같습니다.

## 검증 자료

`user-api/src/test/resources/minigame/`에 모바일 엔진에서 만든 러너·계단·합치기 JSON fixture를 함께 보관합니다. Java verifier 테스트가 같은 seed와 입력을 재생하여 결과를 비교합니다. 서비스 통합 테스트의 검증 대상은 게임 간 기록 격리, 규칙 1·2의 공통 최고점 갱신과 랭킹, 기존 기록 보존, 멱등 제출, 동시성, 롤백과 탈퇴 경합입니다. 규칙 1 fixture의 결과는 바뀌면 안 되며, 규칙 2 fixture를 별도로 추가합니다.

이 검증은 임의 점수 제출과 규칙을 어긴 입력을 차단합니다. 규칙에 맞는 자동 플레이까지 사람의 플레이와 구분하는 인증 수단은 아닙니다. 게임에는 재화 보상을 연결하지 않습니다.

## 배포 전환

1. 규칙 1·2 검증을 지원하는 서버 배포를 완료합니다. 구 앱의 버전 없는 목록·시작 요청은 계속 규칙 1로 처리합니다.
2. 새 앱은 목록·시작에 규칙 2를 명시합니다. 완료 요청은 세션이 발급된 규칙으로 검증하고, 랭킹은 기존 게임별 조회를 사용합니다.

최고점 unique `(game_code, user_id)`와 기존 랭킹 인덱스를 유지하며 스키마 변경이나 기존 기록의 변환·삭제는 수행하지 않습니다. 회원탈퇴는 해당 회원의 모든 게임 세션과 최고점을 같은 트랜잭션에서 삭제합니다. 게임의 재화 보상이나 시즌 초기화는 없습니다.
