회원탈퇴(계정 삭제) — 구현 walkthrough

DELETE /api/v1/me — soft delete + 소셜 연동 해제(revoke) + 즉시 재가입 허용 · 이슈 #225

domain 엔티티·리포지토리·스키마 user-api 컨트롤러·서비스·DTO test 검증 위험영역 정합성 주의

1. 한 줄 요약

로그인한 회원이 DELETE /api/v1/me를 호출하면 계정을 soft delete 하고, 모든 refresh token을 폐기하고, 소셜 연동(oauth_accounts)과 FCM 토큰을 지웁니다. DB 커밋이 끝난 뒤에는 카카오 unlink·애플 revoke를 best-effort로 호출해 provider 쪽 연동까지 해제합니다(앱스토어 심사 가이드라인 5.1.1(v) 요구사항). 같은 소셜 계정으로 다시 로그인하면 새 계정으로 즉시 재가입되며 기존 데이터는 복원되지 않습니다. 이를 위해 애플 로그인 계약도 바뀌어, 로그인 시 authorizationCode를 함께 받아 revoke용 refresh token을 미리 확보·암호화 저장해 둡니다.

한 트랜잭션으로 4가지 정리
users.deleted_at 세팅 + active refresh token 전량 revoked_at 세팅 + oauth_accounts 삭제 + user_device_token 삭제. 하나라도 실패하면 전부 롤백됩니다.
커밋 후 provider 연동 해제 (best-effort)
AFTER_COMMIT 리스너가 카카오 unlink(Admin key)·애플 revoke(저장해 둔 refresh token 복호화)를 호출합니다. 구글은 서버가 보유한 토큰이 없어 row 삭제로 충분. 실패해도 탈퇴는 이미 확정 — 로그만 남깁니다.
204 No Content
응답 본문 없음. 클라이언트는 저장한 토큰을 지우고 로그인 화면으로 이동합니다.

5. 핵심 설계 결정

soft delete — 기존 컬럼 재사용

users.deleted_at에 시각만 세팅하고 row는 남깁니다(hard delete 아님). 신규 migration 없이 기존 스키마를 그대로 쓰고, softDelete는 멱등이라 중복 호출돼도 최초 탈퇴 시각이 보존됩니다.

재가입 허용 = 연동 row 삭제

탈퇴 시 oauth_accounts를 지우면 (provider, provider_user_id) unique 제약이 풀려서, 재로그인이 기존 신규 가입 플로우 그대로 새 계정을 만듭니다. 재로그인 차단 로직도, 전용 에러코드도, 유예기간 판정도 필요 없습니다 — 삭제 하나로 정책이 구현되는 가장 단순한 형태입니다. 옛 계정의 루틴·재화·캐릭터는 soft delete된 옛 user에 남고 새 계정에는 노출되지 않습니다.

provider revoke는 커밋 이후 best-effort

외부 API(카카오·애플) 호출을 트랜잭션 밖(AFTER_COMMIT)에 두어, 애플 서버가 죽어 있어도 탈퇴 자체는 성공합니다. 반대로 revoke가 먼저였다면 외부 장애가 탈퇴를 막았을 것입니다. 기존 FCM push의 best-effort 컨벤션(NotificationService)과 동일한 패턴을 재사용했습니다. 실패는 로그만 남기고 재시도 없음(MVP).

애플 revoke 재료는 로그인 때 미리 확보

애플 revoke API는 access/refresh token을 요구하는데 서버는 identityToken만 받고 있었습니다. 그래서 로그인 계약에 authorizationCode를 추가해, 로그인 성공 시 애플 토큰 엔드포인트에서 refresh token으로 교환한 뒤 AES-256-GCM으로 암호화해 oauth_accounts에 저장합니다(애플 공식 권장 방식). 교환·revoke 호출의 client_secret은 팀 키(.p8)로 서명한 ES256 JWT를 요청 직전에 생성합니다(TTL 300초).

시크릿 fail-closed

신규 시크릿 5종(APPLE_TEAM_ID·APPLE_KEY_ID·APPLE_PRIVATE_KEY·APPLE_REFRESH_TOKEN_ENC_KEY·KAKAO_ADMIN_KEY)은 전부 기본값이 공란이며, 미설정 환경에서는 커밋된 기본 키로 조용히 동작하는 대신 502로 실패합니다. 방어가 소리 없이 꺼지는 것을 막는 기존 컨벤션(카카오 app_id, 애플 aud 검증)과 같은 방향입니다.

탈퇴 계정 잔여 토큰 차단

탈퇴 트랜잭션과 동시에 refresh 회전이 일어나면 전량 폐기 스냅샷을 빠져나간 토큰이 생길 수 있습니다. 그래서 refresh 회전과 dev-login에서 user.deletedAt을 한 번 더 확인해 거부합니다. 신규 에러코드 없이 기존 REFRESH_TOKEN_INVALID/USER_NOT_FOUND를 재사용합니다.

FCM 토큰 삭제 (리뷰 반영)

루틴을 연쇄 soft delete 하지 않기로 했기 때문에, 탈퇴자의 ACTIVE 루틴이 리마인더 배치 후보에 그대로 남습니다. 리뷰에서 "탈퇴한 사용자 단말에 다음날에도 push가 간다"는 문제가 발견되어, 탈퇴 트랜잭션에서 user_device_token을 전량 삭제해 발송 자체를 차단했습니다. 같은 취지로 revoke 실패 로그에서 소셜 식별자(providerUserId)도 제거했습니다.

6. 위험영역 인증·개인정보·migration

bulk delete의 flush 함정. FCM 토큰 삭제는 JPQL bulk delete인데, clearAutomatically만 켜면 아직 flush되지 않은 선행 dirty 변경(softDelete·토큰 revoke)이 영속성 컨텍스트와 함께 버려집니다. 실제로 이 상태에서 통합테스트 5개가 깨졌고, flushAutomatically = true를 함께 켜 "bulk delete 직전에 선행 변경을 DB로 내보낸 뒤 clear" 순서로 고쳤습니다. 같은 이유로 withdraw는 컨텍스트를 clear하므로 외부 트랜잭션에 참여시켜 호출하면 안 됩니다(코드 주석으로 명시).
애플 로그인이 시크릿·외부 API에 의존하게 됐습니다. 토큰 교환이 로그인 성공 경로의 필수 단계라, 애플 시크릿 미주입이나 애플 토큰 엔드포인트 장애 시 애플 로그인 전체가 502로 실패합니다(fail-closed 결정의 트레이드오프). 배포 전 환경변수 주입이 필수이며, 교환 실패 시 로그인은 성공시키는 완화(fail-open)는 정책 변경이라 미결로 남겼습니다.
access token 30분 한계. 이미 발급된 access token은 탈퇴 후에도 만료 전까지 유효합니다(stateless JWT의 알려진 한계, logout도 동일). 이 창에서의 중복 탈퇴 요청은 404로 안전하게 거부됩니다. 즉시 무효화가 필요해지면 블랙리스트 도입을 별도 논의합니다.
migration V36. 신규 파일만 추가했고 기존 V1~V35는 수정하지 않았습니다(checksum 안전). 컬럼 정의가 엔티티와 일치해 ddl-auto: validate를 통과합니다.

10. 아직 안 정한 것 (후속)

사람 결정 대기
  • 애플 로그인 fail-open 여부 — 교환 실패 시 refresh token 없이 로그인을 성공시킬지(현재는 fail-closed로 로그인 실패)
  • 탈퇴 후 개인정보(email·nickname·bio·프로필 key) 파기 정책 — 현재 무기한 보존. 익명화 또는 보관기간 결정 필요
  • house/room/캐릭터/아이템/재화(장진형 도메인)의 탈퇴 회원 처리 — 소유 house 처리, 길드북 닉네임 노출, 잔여 재화 데이터. dependency로만 남김
  • 리마인더 배치가 탈퇴자 루틴을 계속 후보로 잡아 매일 FAILED 알림 행이 쌓임(push는 안 감) — 후보 쿼리에 user.deletedAt is null 필터 추가로 해결 가능
  • 교환·revoke용 client_id를 apple.allowed-client-ids 첫 항목으로 유추 — 목록에 Service ID를 추가하게 되면 별도 프로퍼티 분리 필요
  • revoke 실패 운영 모니터링·알림, 외부 호출 타임아웃 설정
