# 루틴·투두 완료 보상 공통화

2026-10-19 | R5 1차 | 기준 main `484e81d8b9340fdd0d5bfca58597653260df9530`

루틴과 투두의 완료 보상액 계산, 코인 지급, 원장 기록을 `CompletionRewardService`로 모았다. 각 기능의 완료 조건과 상태 변경, 성장 반영 순서는 유지했다. 완료 취소 처리와 보상 정책 변경은 이번 범위에 포함하지 않았다.

## 변경 전과 후

| 책임 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 당일 보상액 계산 | 두 서비스가 각각 10코인과 잔여 한도를 비교 | 공통 서비스의 `calculateAmount` |
| 코인 지급과 원장 기록 | 두 서비스가 직접 지갑을 변경하고 원장을 호출 | `grantRoutineReward`, `grantTodoReward` |
| 일일 합산 한도 | `DailyRewardService` | 그대로 재사용 |
| 방 성장 | `RoomGrowthService` | 각 서비스가 기존 순서로 호출 |
| 완료 조건·상태·스트릭·미션 | 루틴·투두 서비스 | 각 서비스에 유지 |
| 완료 취소와 보상 회수 | 루틴·투두 서비스 | 변경 없음 |

공통 서비스는 기존 `routine.reward.service` 패키지에 둔다. 루틴·투두가 이미 함께 쓰는 일일 보상 계산과 같은 위치다. 공용 지갑 전체를 다시 설계하거나 범용 완료 처리기를 만들지 않는다.

공통 서비스의 클래스에 `@Transactional(propagation = MANDATORY)`를 지정했다. 호출자의 완료 트랜잭션이 있어야 실행되며 새 트랜잭션을 만들지 않는다. 루틴·투두 서비스의 `WalletHistoryRecorder` 의존은 기존 취소 처리에 계속 사용한다.

## 유지할 계약과 실행 순서

- 당일 정가 10 COIN, 루틴·투두 합산 KST 하루 50 COIN. 남은 한도가 10보다 적으면 부분 지급한다.
- 과거 완료, 마감일 없는 투두, 한도 소진은 보상 0이다. 보상 0이어도 완료 자체는 성공하고 원장은 생성하지 않는다.
- 루틴의 당일 스트릭·미션 기여는 보상 0 여부와 별개다. FAILED 전이, SKIPPED 처리, 계보 중복 검사를 유지한다.
- 사용자 → 코인 지갑 잠금을 먼저 잡고 일반 조회와 일일 합산을 수행한다. 공통 서비스는 잠금을 다시 잡거나 새 트랜잭션을 열지 않는다.
- 보상액 계산 → 완료 기록 → 코인 증가 → 원장 기록 순서를 유지한다. 원장에는 실제 지급액과 증가 직후 잔액을 기록한다.
- 루틴의 원장 출처는 `ROUTINE_COMPLETE / ROUTINE_LOG / log.id`, 투두는 `TODO_COMPLETE / TODO / todo.id`다.
- 루틴은 방 성장 후 로그의 성장 지급액을 기록한다. 투두는 성장 지급액을 먼저 기록한 뒤 방 성장으로 넘어간다. 투두의 중간 flush와 UPDATE 한 번을 유지하기 위해 이 차이를 그대로 둔다.
- 루틴 완료의 `TransactionTemplate`과 unique 충돌 후 새 트랜잭션 재시도를 유지한다. 완료·코인·원장·성장은 함께 커밋하거나 롤백한다.

API 경로, 응답 DTO, 오류 코드, DB migration, 취소 시 음수 잔액 처리에는 변경이 없다. 이번 작업은 책임 배치를 정리한 것이며 성능 향상을 측정한 작업은 아니다.

## 검증

변경 전 핵심 범위 15개 클래스의 테스트 158개가 모두 통과했다. 이후 기존 테스트 3개의 원장 검증을 보강하고 생성자 변경에 영향을 받는 루틴·투두 테스트로 범위를 넓혔다. 보강한 검증을 포함한 23개 클래스, 278개가 원본 구현에서 통과한 뒤 공통 서비스를 추출했다.

모듈별 JUnit XML 390개로 집계했다. 파라미터 실행의 중복을 보존해 원본과 변경 후의 관련 278개 실행 항목이 같음을 대조했다. 초기 158개나 확대 검증 278개를 전체 합계에 중복으로 더하지 않았다. 테스트 수를 늘린 작업이 아니라 기존 3개 테스트의 검증을 강화한 작업이며, 건수는 커버리지 비율이 아니다.

생략 10개는 기존 환경 변수로 활성화하는 네이티브 libvips 2개, 실제 FastAPI 1개, 실제 AI 모델 평가 2개, 실제 가구 생성·개발 Lambda 5개다. 이번 작업으로 테스트를 비활성화하지 않았다.

기존 테스트 3개에 다음 내용을 추가했다.

1. 루틴 완료 원장의 `sourceId`가 완료 응답의 실제 로그 ID와 같은지 확인한다.
2. 루틴 부분 지급의 원장 금액 5, 지급 직후 잔액, 통화, 사유, 출처와 ID를 확인한다. 다음 0 지급 완료에는 원장이 없어야 한다.
3. 투두 부분 지급과 다음 0 지급에도 같은 기준을 적용한다.

기존 `RoomGrowthIntegrationTest`는 실제 Spring 서비스 빈으로 혼합 동시 완료, 동시 취소, 지급 이후 전체 롤백, 투두 UPDATE 횟수를 검증한다. 직접 서비스 객체를 만드는 `@DataJpaTest`만으로 트랜잭션 전파를 검증했다고 판단하지 않는다.

직접 서비스를 구성하는 테스트 13개 파일의 생성자 16곳은 새 공통 서비스를 사용하도록 바꿨다. 완료와 취소에 같은 원장 기록 객체를 전달했으며 기존 정책 검증은 삭제하거나 완화하지 않았다. 별도 정합성·트랜잭션 리뷰에서 차단할 결함을 발견하지 못했다.

Java 25와 MySQL 8.4 Testcontainers로 검증했다. HTTP 계약은 MockMvc, 실제 저장·동시성·롤백은 DB 통합 테스트로 확인했으며 운영 배포나 실제 앱 E2E 결과를 뜻하지 않는다. 테스트 컨테이너는 실행 종료 후 정리됐고 기존 로컬 MySQL은 `healthy` 상태를 유지했다.
