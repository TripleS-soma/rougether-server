# 개인 방 성장 운영 소급 반영

## 기준

구간 필요 포인트는 20, 22, 24, …이며 레벨 L의 최소 누적치는 `L × (L + 19)`입니다. 기존 실제 COIN 완료 보상에서 이미 기록한 `growth_reward_amount`를 뺀 양만 추가합니다. 기존 잔액·원장·방 배치는 변경하지 않습니다. 취소된/미완료 이력·0 보상·다른 통화·봇·탈퇴 회원은 제외합니다. 지급액을 보존한 soft delete 이력은 포함합니다.

## 실행 순서

1. 운영 DB의 Flyway 상태와 현재 user-api SHA를 확인하고, 변경 전 사용자별 포인트·레벨·배치 revision·잔액 및 완료 보상 합계를 보관합니다. 비밀번호·토큰·회원 개인정보를 보고서에 출력하지 않습니다.
2. V69/V70 및 새 완료·취소 코드를 배포하고 활성 user-api의 SHA와 직접/HTTPS health를 확인합니다. 배포 중 자동으로 소급하지 않습니다. 구버전 완료 취소는 성장 포인트를 모르므로 새 user-api 전환 전에 소급하면 회수 누락이 생깁니다.
3. 검증한 동일 revision의 `PersonalRoomGrowthBackfill`을 JDBC로 운영 DB에 연결해 실행합니다. `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`는 프로세스 환경으로만 전달하며 명령행 인자나 로그로 출력하지 않습니다.

```bash
./gradlew :domain:classes
java -cp "domain/build/classes/java/main:$MYSQL_DRIVER_JAR" \
  com.triples.rougether.domain.room.migration.PersonalRoomGrowthBackfill
```

4. 적용 후 대상 완료 이력의 `reward_amount - growth_reward_amount` 합이 0인지, 누적 포인트와 현재/최고 레벨이 곡선에 맞는지 확인합니다. 원래 배치·잔액과 차이가 있으면 동시간대 실제 사용자 활동 이력과 대조합니다.
5. 같은 도구를 다시 실행해 추가 포인트 0을 확인합니다. 별도 테스트 사용자로 운영 완료/취소 smoke가 필요한 경우 기존 회원의 이력을 테스트 목적으로 변경하지 않습니다.
6. 임시 JDBC/SSM 터널을 닫고 적용 전후의 집계 수·대상 사용자 수·현재 배포 SHA를 기록합니다.

## 정합성과 재실행

사용자마다 user → coin wallet 잠금을 먼저 잡고 완료 건을 잠근 뒤 성장·레벨·지급 표식을 함께 커밋합니다. 한 사용자의 저장 실패는 그 사용자의 변경을 모두 롤백하며, 앞서 성공한 사용자는 재실행 시 차액이 0이므로 중복 지급되지 않습니다. 완료 행이 물리 삭제되어 근거가 없으면 포인트를 추정하지 않습니다.

모루는 준비된 활성 카탈로그만 지급합니다. 기존 보유(회수 이력 포함)는 다시 지급하지 않고 대표 캐릭터를 바꾸지 않습니다. 비활성/미등록 상태는 최고 달성 레벨을 보존하여 추후 내 방·보유 목록 조회에서 지급합니다.
