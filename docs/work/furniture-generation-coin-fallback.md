# AI 가구 생성의 100코인 대체 결제

2026-11-04 사용자 결정: AI 가구 생성권이 있으면 1회를 먼저 사용하고, 없으면 100코인으로 생성한다.

## 동작

- 접수 시 `GenerationCreditLedger`가 사용자 행, 생성권 계정, 필요한 코인 지갑을 잠근다. 생성권이 1회 이상이면 기존 생성권 예약을 사용하고, 그렇지 않으면 `COIN` 지갑에서 100을 차감한다.
- 생성권과 코인이 모두 부족하면 기존 402 `FURNITURE_CREDITS_REQUIRED`를 반환한다. 지갑이 없으면 코인 잔액을 0으로 취급한다.
- `furniture_credit_reservations.payment_type`과 `payment_amount`에 실제 수단과 금액을 저장한다. `CREDIT`는 1회, `COIN`은 100코인이다. 기존 예약은 CREDIT, 1회로 유지한다.
- 실패, 업로드 중단, 작업 만료 시 저장한 수단으로 한 번만 반환한다. 접수 후 생성권이 지급되거나 코인 잔액이 달라져도 환급 수단은 바뀌지 않는다. 이미 성공한 가구의 피드백 실패는 환급하지 않는다.
- 코인 차감과 반환은 `wallet_histories`에 각각 `FURNITURE_GENERATION`, `FURNITURE_GENERATION_REFUND`로 남긴다. 코인 결제는 생성권 잔액과 예약 수량을 바꾸지 않는다.
- 작업, 결제 예약, 지갑 차감과 원장은 같은 트랜잭션으로 커밋한다. 같은 requestId의 재전송과 중복 정산은 추가 차감이나 환급을 하지 않는다.
- `billing.require-credits=false`는 기존 무료 개발 모드를 유지한다. 운영에서는 true를 사용한다.

## 앱 연동

`GET /api/v1/me/furniture-credits`와 `GET /api/v1/me/wallets`를 함께 조회한다. 생성권이 있으면 `생성권 1회로 만들기`, 없으면 `100코인으로 만들기`를 표시한다. 생성권과 100코인이 모두 없으면 생성 버튼을 비활성화한다. 접수 후와 진행 중 작업 조회 시 지갑도 갱신한다. 기존 사진 업로드와 작업 조회 API 형태는 유지한다.

## 반영 순서

1. V94 마이그레이션과 새 코드를 빌드한다. 관리자 H2와 운영 MySQL에 모두 적용 가능한 개별 ALTER 문을 사용한다.
2. Lambda Control을 새 정산 코드로 먼저 전환한다. 이전 Control은 코인 예약을 생성권으로 해석하므로 신규 코인 접수를 먼저 켜면 안 된다.
3. 사용자 API를 새 접수 코드로 전환한다. 코인 작업이 남아 있는 동안에는 Control의 코인 정산 지원을 유지한다.
4. 앱의 코인 잔액 표시와 생성 조건을 반영한다.

이 문서는 구현과 반영 순서를 기록한다. 운영 반영 여부는 별도 배포 결과로 확인한다.
