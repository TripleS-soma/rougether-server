# 어드민 통계 메모리 최적화 검증 (2026-11-14)

## 변경 범위

비교 기준은 측정 당시 운영에 배포돼 있던 main `4e9b24f1cb3cafd354c7a59db27c8ba6ece686f1`이다. 별도 브랜치 `codex/admin-memory-optimization-20261114`에서 아래 두 항목만 변경했다. 이 비교 실험은 로컬에서 수행했으며 운영 배포, 재시작, JVM 옵션 변경을 수행하지 않았다.

1. 리텐션에서 완료 기록을 건별로 읽고 Java의 Set으로 날짜를 줄이던 처리를 DB의 `(userId, KST 완료일)` DISTINCT로 이동했다. 완료 상태, 봇/AI/탈퇴 제외, `[from, now)` 조건, 완료율 분모, 코호트와 공동집 구분은 유지했다. UTC DB 세션에서 9시간을 더해 LocalDate로 변환한다.
2. 활동 캐시에 Spring projection proxy와 JDBC Tuple을 보관하지 않고 필요한 6개 불변 값을 record로 복사한다. 다른 날짜 조회 시에도 만료된 스냅샷을 함께 제거한다. 15초 TTL, 최대 8개 날짜 LRU, 단일 잠금과 200ms 대기 제한은 유지한다. 유휴 중 즉시 제거하는 별도 타이머는 추가하지 않았다.

## 실험 조건

운영과 분리된 macOS JVM, Java 25.0.3, localhost MySQL 8.4.11이다. 사용자 500명(봇, AI, 탈퇴 각 5명), 루틴 완료 149,708건, 일별 활동 17,500건의 고정 합성 데이터를 사용했다. 한 사용자는 KST 자정과 from/to 경계의 완료 시각으로 대체했다. 실제 저장된 UTC 경계값도 확인했다.

변경 전후를 각각 3회, A/B → B/A → A/B 순서로 실행했다. 다른 회귀 테스트가 끝난 뒤 측정했다. JVM은 두 버전 모두 `-Xmx384m -Duser.timezone=UTC -XX:+UseSerialGC -XX:ReservedCodeCacheSize=128m -XX:MaxMetaspaceSize=256m -XX:MaxDirectMemorySize=64m`다. 외부 JVM 옵션 환경 변수와 운영 접속 변수는 제거했다.

## 해석 범위

요청 할당량은 ThreadMXBean으로 측정한 해당 요청 스레드의 누적 Java 할당량이다. 동시에 살아 있는 객체나 peak heap이 아니므로 힙 상한 384MiB보다 클 수 있다.

캐시 힙은 동일한 캐시 8개를 유지한 상태와 해제한 상태의 로컬 full GC 후 전체 힙 차이를 8로 나눈 추정치다. JPA/JIT 등의 잡음이 포함될 수 있으며 객체별 exclusive retained size는 아니다. 각 버전 3개 유효 표본을 사용했다. 변경 후 만료 직후의 작은 힙 차이는 음수 잡음이 발생해 null로 기록했고, 해당 절감량은 주장하지 않는다. 날짜 엔트리 수 8→1은 별도 직접 측정이다.

RSS는 시작부터 종료까지 전체 JVM의 최대값이며 8개 캐시 부하와 초기화도 포함한다. RSS 감소는 확인되지 않았다. 따라서 이번 결과를 운영의 693.6MiB가 특정 값으로 줄었다는 증거로 사용할 수 없다. 운영 반영 후 실제 조회 패턴의 working set과 GC를 따로 확인해야 한다.

DB DISTINCT에는 중복 제거 비용이 추가된다. 로컬 요청시간은 줄었지만 JVM 메모리 감소를 DB까지 포함한 전체 시스템 자원 절감으로 확대하지 않는다.

초기 워밍업 실험과 한 개 캐시의 힙 차이가 음수로 나온 실험은 측정 방법을 보완하기 위한 예비 실험으로 분리했다. 위 표에는 UTC fixture와 8개 캐시 프로토콜을 고정한 마지막 6개 실행만 사용했으며 이 6개 중 제외한 실행은 없다.
