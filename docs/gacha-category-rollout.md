# 뽑기 세 카테고리 이행 검증

신규 앱의 장식 뽑기는 벽지·바닥·가구 세 종류입니다. 기존 테마 머신의
실제 운영 풀을 V66에서 복사하며, 기존 머신·캐릭터·악세사리의 획득 API는 유지합니다.

## 배포 순서와 호환성

새 모바일은 `GET /api/v1/gacha?catalog=category` 응답의 `category`와 실제 `gachaId`로
머신을 선택합니다. `catalog`를 생략한 기존 API는 테마·캐릭터 목록을 유지하고 신규
카테고리 머신을 제외합니다. 지원하지 않는 `catalog`는 `400 VALIDATION_FAILED`입니다.
V66은 기존 머신을 중지하지 않으므로 구버전 앱의 목록과 캐시된 ID가 계속 동작합니다.
구머신 종료는 별도 이행에서 결정합니다. 기존 목록을 클라이언트에서 임의로 합치거나
가짜 ID를 발급해서는 안 됩니다.

V66은 정식 세 머신을 **비활성으로 준비**합니다. Flyway는 신규 후보 서버의 시작 시점에
실행되므로 이때 아직 요청을 받는 구서버에 활성 머신이 보이면 안 됩니다. 구서버는
`catalog` 구분을 모르며 `themeId=null` 머신을 구앱이 캐릭터로 해석할 수 있습니다.
DB migration은 이미지 롤백으로 되돌아가지 않습니다. 따라서 다음 두 단계를 분리합니다.

1. V66을 포함한 서버 전체 배포를 완료합니다. 세 머신은 비활성이고 새 목록은 비어
   있어야 합니다. 기존 목록·캐시된 ID는 유지됩니다. 카테고리 머신을 요구하는 관리자
   신규 장식 import·등급 지정은 이 준비 구간에 차단되므로 함께 중지합니다.
2. user-api만 전환된 시점이 아니라 admin-api·batch까지 **전체 배포 성공**을 확인하고,
   아래의 활성화 조건과 운영 승인을 모두 충족한 뒤 세 머신을 한 트랜잭션으로 켭니다.

이 변경 자체는 운영 DB 수정·배포 완료를 의미하지 않습니다. 배포 직전 최신 main의
Flyway 번호와 V66 충돌 여부를 확인합니다. V61–V65는 별도 변경이므로 운영에 아직
적용되지 않았다면 함께 실행될 내용을 먼저 검토한 뒤 배포 범위를 확정합니다.

## 데이터 편입 범위

V66은 현재 시작된 활성 상시 머신의 활성 ITEM 엔트리를 배치 유형으로 분류합니다.
벽지와 바닥은 `surface_slot`의 정확한 슬롯값을 확인하고, 러그를 포함한 `positioned`
아이템은 가구로 보냅니다. 배경·캐릭터 악세사리·상충하는 배치 정보는 제외합니다.

종료일이 있는 한정 머신, 아직 시작하지 않은 머신, 비활성 머신과 풀은 편입하지
않습니다. 같은 아이템의 중복은 한 행으로 합치며 등급 충돌은 전설·희귀·일반 중
최상위 지원 등급을 보존합니다. 기존 등록에 등급이 없으면 일반입니다. 아이템이나
테마 자체가 비활성이어도 기존 풀 등록은 유지하며, 사용자 조회와 추첨의 활성
필터가 실제 배출을 막습니다. 기존 머신·풀 행과 이력 ID는 삭제하지 않습니다.

상점에만 있고 뽑기 풀에 한 번도 등록되지 않은 기존 상품에는 이번 이행이 새 확률을
부여하지 않습니다. 따라서 특정 카테고리가 비어 있을 수 있습니다. 운영 전
진단에서 풀이 비어 있으면 활성화를 중지합니다. 비활성 머신은 관리자 등급 지정도
차단하므로 이 준비 구간을 정상 API로 채울 수 없습니다. 편입 아이템·등급에 대한 별도
승인과 검토된 DB 보완 또는 전용 준비 절차가 완료된 뒤 처음부터 재검증합니다.
카테고리 머신 활성화 이후 신규 카탈로그 적재에서 활성 장식은 일반 등급으로 자동 등록되지만,
기존 상품 재적재는 원래 등급과 회수 상태를 보존합니다.

## 읽기 전용 진단

`deploy/sql/verify_gacha_categories.sql`은 모두 SELECT인 MySQL 8 진단 스크립트입니다.
승인된 운영 연결에서 이행 전후 각각 실행해 결과를 보관합니다. 새 목록은
`GET /api/v1/gacha?catalog=category`, 기존 목록은 `GET /api/v1/gacha`로 각각 검증합니다.

- 세 정식 코드가 각각 한 개이고 25 COIN·1회·테마/기간 없음인지 확인합니다.
  V66 직후에는 세 개 모두 비활성, 별도 활성화 성공 후에는 세 개 모두 활성이어야 합니다.
- 기존 머신 ID와 활성 상태가 이행 전후 동일하며 기존 앱 조회와 추첨이 유지되는지 확인합니다.
- `eligible_catalog_count`와 `included_pool_count`의 차이 및 누락 상세를 비교합니다.
  `gap_count`는 의도적으로 제외한 상품도 포함하므로 자동 편입의 근거로 사용하지 않습니다.
- 세 카테고리의 `included_pool_count`가 모두 1 이상이어야 뽑기 화면을 완전하게 운영할 수 있습니다.
  이 값은 머신 활성 상태와 무관한 준비된 유효 풀의 개수이며 첫 쿼리의 `is_active`와 구분합니다.
  활성 머신의 비어 있는 풀은 `GACHA_EMPTY_POOL`을 반환하며 코인·보상 이력을 남기지 않습니다.
- 중복 활성 등록과 잘못된 보상 조회는 0행이어야 합니다.
- 등급별 보상 수를 확인합니다. 빈 등급은 기존 계약대로 전체 유효 풀 균등 추첨으로
  대체되므로 모든 풀에서 유효한 실효 확률이 70/25/5인 것은 아닙니다.

이행 후 테스트 계정으로 각 카테고리 미리보기·1회·5+1회와 중복 환급을 확인합니다.
기존 캐릭터 직접 API와 온보딩 획득도 함께 확인합니다. 운영 재화 차감 검증은
운영자가 승인한 테스트 계정·범위에서 수행합니다.

## 별도 활성화 — 운영 승인 후에만 실행

현재 코드·테스트 작성 자체로 이 단계가 승인되거나 실행된 것은 아닙니다. 카탈로그
관리자 변경과 다른 배포를 잠시 중지하고 다음 증빙을 하나의 배포 기록에 보관합니다.
배포 실행을 맡은 주 담당자가 아래 외부 상태를 직접 실측한 증빙이 없으면 활성화할 수 없습니다.

- 승인된 전체 40자리 release SHA와 배포 workflow의 최종 성공 결과를 확인합니다.
- EC2 배포 상태 파일의 `DEPLOYMENT_STATUS=ready`, `DEPLOYED_SHA`, `TARGET_SHA`를 대조합니다.
  user-api·admin-api·batch 실행 컨테이너의 실제 이미지 SHA도 같은 release여야 합니다.
- 공용 user-api health와 admin health, batch health가 정상인지 확인합니다. 후보 컨테이너의
  내부 health만으로 승인하지 않습니다. 신규 서버의 `catalog=category` 빈 목록과 기본
  legacy 목록을 확인하여 단순 200 응답과 카테고리 호환 코드 적용을 구분합니다.
- 이전 user-api·admin-api 슬롯의 drain 완료 및 컨테이너 정지, 프록시가 신규 슬롯을
  가리키는 상태를 확인합니다. 진행 중 배포나 자동 rollback trap이 남아 있으면 중지합니다.
- 진단 SQL로 **실제 ID 세 개**, 코드, 비활성 상태, 25 COIN·1회·기간/테마 없음,
  각 활성 엔트리 수와 등급 분포를 다시 확인합니다. 2026-09-06 관측값을 그대로 신뢰하지 않습니다.
  활성 엔트리는 모두 활성 아이템·테마에 속하는 적격 단일 ITEM, 지원 등급, weight=1이어야
  합니다. 비활성 아이템/테마 등록은 보존되지만 초기 활성화 guard를 통과하지 못하므로
  차이가 있으면 자동 보정 없이 승인 범위를 다시 검토합니다.

`deploy/sql/install_gacha_category_activation.sql`은 `SQL SECURITY INVOKER` 루틴 두 개만
설치하며 머신 상태는 바꾸지 않습니다. 운영 연결에 `CREATE ROUTINE`, `EXECUTE`와
관련 테이블 권한이 필요합니다. CREATE/DROP은 데이터 CALL과 별개의 DDL이며 기존
동명 루틴을 덮어쓰지 않습니다. 설치가 실패하면 `--force`로 계속하지 말고 정의와
설치 이력을 확인합니다. 진행 중 트랜잭션이 없는 새 연결을 사용합니다.
첫 루틴 생성 후 두 번째 생성이 실패하면 첫 루틴은 남습니다. 데이터는 아직 변경되지
않았지만 자동 제거·덮어쓰기 없이 두 루틴의 `SHOW CREATE PROCEDURE`와 설치 결과를
대조해 복구합니다. 두 루틴이 검토한 원문과 일치하기 전에는 어느 CALL도 실행하지 않습니다.

활성화 CALL의 인자는 벽지 ID·바닥 ID·가구 ID, 각 **활성 엔트리 수**, 승인 SHA,
실측 SHA, 전체 배포 ready·공용 health·구슬롯 drain 확인 순서입니다. 아래는 실행
템플릿이며 NULL을 전부 검증한 값으로 대체하기 전에는 실패합니다. 세 TRUE는 SQL이
외부 시스템을 확인했다는 뜻이 아니라 위의 실측 증빙에 대한 운영자의 확인입니다.

```sql
CALL activate_gacha_categories_v66(
    NULL, NULL, NULL,
    NULL, NULL, NULL,
    NULL, NULL,
    NULL, NULL, NULL
);
```

루틴은 SERIALIZABLE 트랜잭션에서 머신·풀·아이템·테마의 읽기/쓰기 잠금을 유지하며,
ID/코드·가격·기간·활성 상태·개수·자격·중복·등급 중 하나라도 불일치하면 `45000`으로
중단합니다. UPDATE 도중 오류도 EXIT HANDLER가 전체 ROLLBACK 후 원래 오류를 반환합니다.
지갑·보유 아이템·기존 머신·기존 풀은 수정하지 않습니다. 오류나 연결 결과 불명확 시
맹목적으로 재실행하지 않고 새 연결에서 세 머신의 실제 상태를 조회합니다.

성공 후 새 연결의 진단 SQL에서 정확히 세 개 활성, 기존 머신 ID/상태 불변을 확인하고
`GET /api/v1/gacha?catalog=category`에서 `WALLPAPER/FLOOR/FURNITURE` 순서의 실제 세 ID,
기본 `GET /api/v1/gacha`에서 canonical ID가 빠졌는지 확인합니다. 그다음 승인된 테스트
계정 smoke와 모바일 공개를 진행합니다. SQL 성공만으로 기능 배포 완료를 선언하지 않습니다.

## 이미지 롤백 경계

초기 배포 중 실패하면 아직 세 머신이 비활성이므로 기존 자동 이미지 rollback이
신규 카테고리를 노출하지 않습니다. 활성화 이후에는 **카테고리 미지원 이미지로
수동 롤백하기 전에** 아래 CALL로 세 개를 먼저 비활성화하고 독립 SELECT로 확인합니다.
자동 배포 스크립트에 이 DB 작업이 추가된 것은 아니므로 자동으로 처리된다고 가정하지 않습니다.

```sql
CALL deactivate_gacha_categories_v66(NULL, NULL, NULL);
```

인자는 활성화 때 보관한 벽지·바닥·가구의 정확한 ID입니다. 이 루틴은 ID/코드 일치만
강제하며 긴급 비활성화를 막지 않도록 풀·가격·현재 활성 개수를 전제하지 않습니다.
반복 실행도 안전하고 다른 머신은 건드리지 않습니다. 새 연결에서 세 개 모두 비활성,
legacy 머신 불변 및 새 목록이 비었음을 확인한 뒤 프록시/이미지를 되돌립니다. 확인에
실패하면 구이미지로 전환하지 않습니다. 이후 재활성화는 전체 활성화 절차를 다시 수행합니다.

호환 구버전으로의 rollback 가능 기간 동안 두 루틴과 승인된 SQL 원문을 보존합니다.
그 기간이 끝났다는 별도 확인 후에만 정확한 두 루틴을 제거할 수 있습니다.

```sql
DROP PROCEDURE activate_gacha_categories_v66;
DROP PROCEDURE deactivate_gacha_categories_v66;
```
