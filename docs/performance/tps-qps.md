# 1,000 / 1,500 RPS 실험의 업무 TPS와 DB QPS

11월 8일 보관된 실험 기록을 다시 계산했다. 세 API(내 정보·오늘 조회 각 40%, 투두 완료 20%)와 모바일 76종 재생은 요청 분포가 달라 별도로 읽는다.

- **업무 TPS**는 DB에서 확인된 서로 다른 투두 완료 수를 해당 회차의 k6 측정 시간(`http_reqs.count / http_reqs.rate`)으로 나눈 값이다. CSV에는 클라이언트가 성공으로 확인한 투두 TPS도 따로 적었다. 두 구형 회차에서는 DB의 완료 수가 성공 응답보다 한 건 더 많았다. 읽기를 포함한 성공 요청률도 별도 열에 있다.
- **DB QPS**는 본부하 안의 첫·마지막 MySQL 전역 `Questions` 누적값 차이를 두 DB 표본의 실제 시각 차이로 나눴다. 약 300초의 HTTP 구간 안에서 DB 표본이 덮는 약 296초를 사용했다. 클라이언트가 보낸 SQL 문장에는 조회, 쓰기, 세션 명령, 모니터링 SQL이 포함된다. [MySQL Questions 정의](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html#statvar_Questions)
- DB가 받은 명시적 COMMIT/초도 CSV에 따로 남겼다. 읽기 트랜잭션도 COMMIT할 수 있어 투두 완료 TPS와 숫자가 다르다. 아래 수치는 실제 발생률이며 최대 처리 능력은 구하지 않았다.
- **미수집**은 그 회차 자체의 QPS를 계산할 분자가 없다는 뜻이다. 최종 1,500 RPS 세 회차의 `diagnostics.json`에는 본부하 DB 표본이 0개였고, 당시 RDS의 Performance Insights 보관 지표 조회도 `NotAuthorizedException`이었다. 예열·다른 회차의 QPS를 대입하지 않았다.

## 11월 8일 추가 계측

격리 ECS의 사용자 API 두 대 중 한 대를 중단한 별도 회차에서, 본부하 직전과 종료 직후 MySQL 전역 Questions를 수집했다. 147.335초 동안 49,733에서 118,693으로 증가해 **468.05 DB QPS**였다. 같은 구간에 HTTP 8,840건을 처리해 **60.00 HTTP RPS**, 서로 다른 투두 1,473개의 완료와 보상을 DB에서 확인해 **10.00 업무 TPS**였다. 이전 1,500 RPS 회차 중 카운터가 없는 행은 미수집으로 유지한다.
