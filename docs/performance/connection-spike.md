# 왜 SQL은 줄었는데 커넥션 풀에서는 계속 기다렸을까?

2026년 11월 7일, 사용자 API 1대와 RDS MySQL `db.m6g.large`에서 1,500 RPS를 보낸 5분을 다시 읽었다. **느린 두 초에 요청이 기다린 곳은 애플리케이션의 커넥션 풀이었다.** 두 표본 모두 40개가 전부 사용 중이었고, 커넥션을 빌리려는 스레드 160개가 기다리고 있었다. 같은 시각 DB에서 커널과 RDS 관리 프로세스의 CPU 사용이 늘었다. 어떤 관리 작업이나 SQL이 먼저 지연을 일으켰는지까지 식별되는 기록은 없다.

## 줄어든 조회와 줄지 않은 대기

`GET /api/v1/me`는 회원 정보, 온보딩 목표, 대표 캐릭터를 응답한다. 변경 전에는 목표와 캐릭터를 따로 읽었고, 변경 후에는 조인 한 번으로 읽는다. 반복 요청의 SELECT는 실제 MySQL 테스트에서 3회에서 2회로 줄었다. 전후 모두 `MemberService.getMe`의 읽기 트랜잭션 안에서 조회한다. **SQL을 한 번 덜 보내는 것과 풀에서 커넥션을 한 번 덜 빌리는 것은 다르다.**

| 첫 30초 제외, 혼합 부하 전체 | 변경 전 | 변경 후 |
|---|---:|---:|
| 커넥션 획득 횟수 | 403,530회 | 403,655회 |
| 빌린 후 반납까지 평균 (`usage`) | 8.49ms | 6.29ms |
| 커넥션을 얻기까지 평균 (`acquire`) | 5.74ms | 5.81ms |
| 표본당 사용 중인 커넥션 평균 | 13.69개 | 10.02개 |
| DB CPU 평균 (I/O wait 포함) | 88.18% | 88.84% |

커넥션을 **빌려 쓰는 시간**은 이번 회차에서 짧아졌다. 하지만 **빌리기 전 대기**는 줄지 않았다. 대기가 짧을 때 남던 커넥션이 피크에 쓰도록 따로 쌓이는 것은 아니기 때문이다. DB CPU는 세 API와 DB 호스트 전체의 값이다. 실제로 두 회차의 커널 CPU 평균은 19.22% → 15.52%, nice 항목은 52.48% → 59.88%로 서로 반대 방향으로 움직였다. 이 값만으로 조인의 SQL 단독 CPU 비용을 계산할 수는 없다.

## 14:33:20에 무엇이 보였나

모든 시각은 KST다. HTTP p95는 그 초에 **응답이 끝난** 요청들이다. 풀은 각 초의 약 0.2~0.4초 시점 표본이고, 획득·점유 평균은 직전 표본에서 해당 표본까지 누적 타이머의 차이다. 따라서 한 행을 한 요청의 시간 분해로 읽거나 두 평균을 HTTP p95에서 빼면 안 된다.

| 시각 | HTTP p95 | 사용 / 대기 | 획득 평균 | 점유 평균 | DB CPU 전체 / 커널 | RDS 관리 그룹 CPU |
|---|---:|---:|---:|---:|---:|---:|
| 14:33:19 | 156ms | 6 / 0 | <0.01ms | 3.37ms | 86.9% / 9.0% | 1.0% |
| **14:33:20** | **461ms** | **40 / 160** | **58.93ms** | **25.05ms** | **96.6% / 38.5%** | **10.5%** |
| **14:33:21** | **349ms** | **40 / 160** | **101.67ms** | **24.27ms** | **99.5% / 20.5%** | **3.5%** |
| 14:33:22 | 41ms | 4 / 0 | 52.43ms | 17.22ms | 95.4% / 17.8% | 1.0% |
| 14:33:23 | 9ms | 7 / 0 | <0.01ms | 3.36ms | 86.7% / 13.7% | 0.5% |

- **요청이 밀리고 다시 빠졌다.** 20초에 1,500건을 보냈지만 응답 완료는 1,315건이었다. 21초에는 1,499건을 보내고 1,910건이 끝났다. 두 초의 내 정보 p95는 435/314ms, 오늘 조회는 467/353ms, 투두 완료는 464/368ms였다. 특정 API 하나만 느려진 모양이 아니다.
- **DB 활동의 구성이 바뀌었다.** 19 → 20 → 21초에 기록된 `mysqld` 스레드 CPU 합계(프로세스 행 제외)는 79.5 → 47.0 → 95.0%였다. 20초에는 커널과 관리 그룹이 더 많이 보였고, 21초에는 MySQL 쪽 CPU 사용이 다시 커졌다. 커널 CPU와 관리 그룹은 분류 기준이 달라 합산하지 않는다. 관리 그룹은 개별 작업명이 아니다.
- **디스크나 GC의 긴 정지를 뒷받침하는 동시 표본은 없다.** 두 초의 DB I/O wait는 1.5/0.5%, 데이터 디스크 평균 await는 0.42/0.45ms였다. API의 GC 정지 증가분은 0/11ms였고, 발생기 CPU는 9.4/28.6%, 미발행은 0이었다. 1초 평균으로 개별 COMMIT의 꼬리 지연까지 배제할 수는 없다.
- **관리 그룹 활동만으로는 충분한 설명이 아니다.** 같은 본 측정의 14:31:20에도 관리 그룹 CPU가 11.5%였지만 HTTP p95는 116ms였다. 14:23:20, 14:28:20, 14:38:20에도 비슷한 활동이 있었다. 이번 피크는 매분 00초가 아니라 **33분 20~21초**였다.

가장 잘 맞는 해석은 **이미 빌린 커넥션의 반납이 한동안 늦어지고, 계속 들어오던 요청들이 같은 풀 앞에 줄을 서면서 여러 API의 꼬리 지연이 커졌다**는 것이다. 다만 `usage`는 DB 안의 실행 시간뿐 아니라 앱이 커넥션을 빌리고 있던 전체 시간이다. 이번 경량 실행에서는 SQL digest, 잠금·COMMIT 이벤트, JFR 요청별 추적을 수집하지 않았다. 어떤 쿼리가 커넥션을 점유했는지, 개별 461ms 중 몇 ms를 풀에서 썼는지, RDS의 특정 관리 작업이 원인이었는지는 확정할 수 없다.
