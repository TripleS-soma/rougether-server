# 배치만 꺼지면 Webex가 언제 알려주나?

2026년 11월 7일, 배치 컨테이너 종료 후 **8분 8초**에 장애 메시지 전송이 성공했다. 컨테이너를 다시 시작한 뒤 **2분 0초**에 복구 메시지 전송이 성공했다. 1회 측정이며, 기준은 개발 알림방에 대한 **Webex 메시지 생성 API의 HTTP 200 응답**이다. 수신자 기기에 푸시가 표시된 시각은 측정하지 않았다.

| 상태 | Docker 종료 또는 시작 (KST) | CloudWatch 상태 전환 | Webex HTTP 200 | Docker → Webex |
|---|---:|---:|---:|---:|
| 장애 | 16:43:15.984 | 16:51:20.568 | 16:51:23.840 | 487.856초 |
| 복구 | 16:51:21.241 | 16:53:20.569 | 16:53:21.232 | 119.991초 |

[배치 헬스 1/0으로 바꾼 뒤 같은 환경에서 비교한 결과](batch-health-comparison.md)

## 무엇을 껐나

지난 배치 복구 실험과 같은 로컬 Docker 이미지로 사용자 API, 배치, MySQL을 격리 네트워크에서 실행했다. 셋이 정상일 때 배치에만 SIGKILL을 보냈고, 시험용 CloudWatch 경보가 장애로 전환된 뒤 같은 배치 컨테이너를 다시 시작했다. 중단 중 16:44~16:51의 매분 표본 8개에서 사용자 API 헬스는 모두 HTTP 200이었고 MySQL은 매번 `SELECT 1`에 1을 반환했다.

실험용 수집기는 실행 중인 컨테이너의 cgroup에서 working set을 읽고 약 1분마다 발행했다. 배치가 멈추면 사용자 API 표본만 계속 올라간다. 테스트 네임스페이스에서 `Service=batch`의 표본 수를 평가했다. 1분 단위 2개 중 2개가 임계치 1 미만이거나 누락되면 장애로 처리하는 설정이다. 초기 상태가 OK일 때 알림을 활성화했다. 상태 강제 변경 없이 실제 지표로 전환을 일으켰다.

## 왜 장애 알림이 2분보다 늦었나

이번 실행에서 마지막 배치 표본은 16:43분 구간에 들어갔다. CloudWatch가 장애로 전환하기까지 **8분 5초**, 그 뒤 SNS와 Lambda를 거쳐 Webex가 성공을 반환하기까지 **3.272초** 걸렸다. 지연 대부분은 경보 판정 전에 발생했다. CloudWatch는 누락을 평가할 때 지정한 구간보다 오래된 실측 표본도 참조할 수 있다. 매 평가의 내부 선택 내역까지는 알 수 없다. [AWS의 누락 데이터 평가 규칙](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html)

## 복구 알림을 받으면 배치 작업도 재개됐나

16:52분 구간에 배치 메모리 표본이 다시 들어왔다. Webex가 복구 메시지를 수락한 직후인 **16:53:22에도 배치 헬스는 HTTP 응답이 없었다.** 헬스에서 **200을 확인한 시각은 16:54:44**였다. 이 경보로 확인되는 것은 배치 컨테이너의 표본이 다시 수집됐다는 사실이다. 작업이 예정대로 끝났는지를 보려면 마지막 성공 시각이나 만료 예정 시각을 넘긴 미처리 건을 따로 확인해야 한다. 수집기가 멈춰도 같은 지표 누락이 발생할 수 있으므로 장애 때는 사용자 API 표본도 함께 확인한다.

## 알림 시각 검증과 정리

각 상태 전환 전후 15초에 같은 SNS 토픽으로 성공한 경보 작업은 이번 훈련 한 건씩이었다. 전달 Lambda에도 각 구간에 Webex HTTP 200이 한 건씩 기록됐다. 상태 전환부터 Webex 성공까지는 장애 3.272초, 복구 0.663초였다. 봇의 방 메시지 목록 조회가 403을 반환해 Webex 메시지 자체의 생성 시각은 확보하지 못했다.
