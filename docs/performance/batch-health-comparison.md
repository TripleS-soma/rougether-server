# 배치 장애를 3분 안에 알렸나?

2026년 11월 7일, 30초마다 배치 헬스를 측정한 회차에서는 종료 후 **1분 37초**에 Webex가 장애 메시지를 수락해 3분 목표를 충족했다. 재시작 후에는 **1분 59초**에 복구 메시지를 수락했고, 그보다 **37초 앞서** 헬스에서 HTTP 200과 `UP`을 확인했다.

| 방식 | 배치 종료 → Webex 장애 | 배치 재시작 → Webex 복구 | 복구 알림을 보낼 때의 헬스 |
|---|---:|---:|---|
| 1분 메모리 표본 누락 | 8분 8초 | 2분 | 수락 직후에도 HTTP 응답 없음 |
| 60초 헬스 1/0 | 3분 43초 | 3분 59초 | 첫 `UP` 확인 2분 36초 후 Webex 수락 |
| 30초 헬스 1/0 | 1분 37초 | 1분 59초 | 첫 `UP` 확인 37초 후 Webex 수락 |

각 방식은 한 번씩 측정했다. 시각의 기준은 Docker의 컨테이너 종료·시작 기록과 Webex 메시지 생성 API의 HTTP 200 응답이다. 수신자 기기의 푸시 표시 시각은 확인하지 않았다.

## 어떻게 비교했나

같은 격리 Compose 환경에서 MySQL과 사용자 API를 유지했다. 초기 정상 표본 직후 배치만 강제 종료해 다음 표본까지의 대기 시간도 포함했다. 장애 전환을 확인하면 같은 컨테이너를 재시작했다. 각 수집 때 사용자 API 헬스는 200, DB의 `SELECT 1`은 1이었다. 재시작 후 헬스는 별도로 약 3초 간격으로 조회했고, 첫 정상 **관측** 시각을 사용했다.

30초 회차에서는 EC2 배포 스크립트가 생성하는 수집기를 실행했다. 로컬에서는 격리 네트워크를 통해 같은 배치 헬스 엔드포인트에 접근했고, 테스트 네임스페이스에 고해상도 지표를 발행했다. CloudWatch, SNS, Lambda, Webex는 기존 개발 알림 경로를 사용했다. 두 전환 각각의 전후 15초에 해당 토픽으로 성공한 경보 작업과 Webex HTTP 200 로그가 한 건씩이었다. 임시 경보는 각 회차 종료 후 삭제했다.

## 어떤 상태에서 경보가 풀리나

전용 타이머가 30초마다 `/actuator/health`를 조회한다. HTTP 200이며 본문의 최상위 `status`가 `UP`일 때 1, 연결 실패·시간 초과·그 밖의 응답은 0이다. CloudWatch는 연속된 30초 구간 두 개의 최솟값이 모두 0이면 장애로 판정한다. 수집기가 발행하지 못한 구간도 장애로 평가하도록 설정했다.

이번 측정에는 재시작됐지만 헬스가 아직 올라오지 않은 구간이 있었다. 그동안 0이 계속 기록됐고 1이 들어온 다음에 복구 알림이 발송됐다. 밀린 집 미션이 처리됐는지까지 확인하려면 작업의 성공 기록을 봐야 한다. 개발 계정의 상시 경보 이름은 `rougether-dev-batch-unhealthy`이며, 배포 후 타이머와 경보 상태를 확인하는 절차는 [모니터링 운영 문서](../../deploy/terraform/monitoring/README.md)에 있다.
