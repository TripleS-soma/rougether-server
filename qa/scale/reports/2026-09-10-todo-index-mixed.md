# Todo 복합 인덱스와 206만 건 혼합 부하 비교

후보 인덱스는 오늘 조회의 탐색량을 약 106행에서 3행으로 줄였다. 하지만 일반 읽기 예열의 4회 비교에서는 처리 건수 평균이 3.5% 늘었고, 전체 p95는 개선되지 않았다. 인덱스를 모두 순차 읽어 둔 별도 비교에서는 처리 건수가 9.2% 늘고 전체 p95가 5.8% 줄었다. 두 조건 모두 3,000 RPS 목표에는 미달했다.

인덱스를 통한 누적 이력 조회 개선은 확인했다. 이 실험만으로 3,000 RPS 병목이 해결되었다거나, 처리량이 항상 9.2% 증가한다고 주장할 수 없다. 일반 예열은 조건별 2회, 요청 계수가 맞은 인덱스 예열 비교는 조건별 1회다.

## 조건과 변경

- 격리한 로컬 Rougether 서버의 실제 JWT 인증, `/me`, `/today`, `/todos/{id}/complete` 사용.
- 사용자 20,000명, 측정일의 활성 todo 60,000건, 과거 완료 todo 2,000,000건. 실제 COUNT로 총 2,060,000건 확인.
- 사용자마다 과거 이력 100건. 기한을 넘겨 완료한 무보상 모델이며, 완료일은 측정일보다 최소 30일 이전이다. 오늘 조회·오늘 보상 한도에 포함되지 않는다.
- 읽기 80% / 완료 20%, 고정 도착률 3,000 RPS × 30초. 계획 요청 90,000건, preallocated/max VU 모두 1,000.
- 읽기 100 RPS × 60초 예열. 전체 사용자와 쓰기 경로의 예열을 보장하지 않는다.
- API 4 CPU / 2GiB / heap 1GiB, MySQL 2 CPU / 2GiB / buffer pool 1GiB, Hikari 20개.
- Docker Desktop VM은 12 CPU / 8,217,165,824 bytes 메모리. 호스트 48GB 전체를 DB에 할당한 실험이 아니다.
- `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, binlog ON. 매 회차 새 DB를 만들고 종료 후 삭제했다.
- 동일 JAR SHA-256: `f397889a244376d67ee396922013ca49635b0582212f13551c4223d61c482dec`.
- source SHA `966cf142e343d687698e03ecd1b8e5b4bf3c4a70`. 애플리케이션 코드·운영 설정·Flyway migration은 변경하지 않았다.

기존 인덱스를 유지하면서 일회용 DB에 아래 두 인덱스만 추가했다. 두 조건 모두 `ANALYZE TABLE todos`를 수행했다.

```sql
CREATE INDEX qa_todos_user_deleted_due
    ON todos(user_id, deleted_at, due_date);
CREATE INDEX qa_todos_user_status_completed
    ON todos(user_id, status, completed_at);
```

## 일반 읽기 예열: 기존 → 후보 → 후보 → 기존

| 회차 | 인덱스 | 업무 성공 | 미시작 | 전체 p95 | 완료 API p95 | 평균 연결 획득 대기 | 버퍼풀 미스 읽기 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 기존 | 64,934 | 25,067 | 783ms | 772ms | 69.71ms | 0 |
| 2 | 후보 | 64,585 | 25,416 | 790ms | 779ms | 69.60ms | 5,024 |
| 3 | 후보 | 68,933 | 21,068 | 738ms | 721.75ms | 65.92ms | 4,876 |
| 4 | 기존 | 64,064 | 25,937 | 722ms | 707ms | 70.54ms | 0 |

기존의 성공 건수 평균 64,499 → 후보 66,759로 3.5% 증가했다. 회차별 전체 p95의 산술평균은 752.5 → 764ms, 완료 API p95의 산술평균은 739.5 → 750.375ms였다. 이 평균은 요청을 합쳐 계산한 p95가 아니다. 반복 간 편차가 있어 작은 처리량 차이를 확정적인 효과로 해석하지 않는다.

오늘 조회 SQL의 부하 구간 평균 실행 시간은 기존 0.675–0.796ms, 후보 0.362–0.406ms였다. 두 회차 평균끼리 비교하면 약 48% 감소했다. 같은 SQL이 조사한 행 수는 약 106 → 3행이었다. 이 수치는 Performance Schema의 전후 스냅샷에 모두 존재하는 digest의 차이로 계산했다.

후보에만 약 5천 회의 `Innodb_buffer_pool_reads` 증가가 관측되어, 새 인덱스의 초기 캐시 상태가 섞였다는 가설로 추가 대조를 수행했다. 이 카운터는 버퍼풀에서 처리하지 못해 읽기가 필요했던 요청을 뜻한다. 파일·OS 캐시까지 분리한 SSD 지연 측정은 아니다. [MySQL 상태 변수 정의](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html#statvar_Innodb_buffer_pool_reads)

## 모든 todo 인덱스를 순차 읽은 추가 대조

`--warm-todo-indexes`로 기존·후보 각각의 모든 todo 인덱스를 한 번 읽은 후 동일한 읽기 예열과 본 부하를 실행했다. 예열용 SQL에만 `FORCE INDEX`를 사용했으며, 실제 업무 쿼리의 인덱스는 옵티마이저가 선택했다. 각 인덱스 COUNT가 2,060,000인지 확인했고, 아래 모든 회차의 부하 구간 버퍼풀 미스 읽기는 0이었다. [MySQL 인덱스 힌트 정의](https://dev.mysql.com/doc/refman/8.4/en/index-hints.html)

| 회차 | 인덱스 | 업무 성공 | 미시작 | 계수 합계−계획 | 전체 p95 | 완료 API p95 | 평균 연결 획득 대기 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 후보 | 73,301 | 16,700 | +1 | 665ms | 651ms | 62.35ms |
| 6 | 기존 | 67,803 | 22,159 | −38 | 703ms | 689ms | 66.92ms |
| 7 | 기존 재측정 | 67,120 | 22,880 | 0 | 706ms | 700ms | 67.73ms |

6회차는 발송+미시작 합계가 계획보다 38건 부족했다. 업무 성공 수와 서버 처리 완료 수는 일치했지만, 계획 요청 계수 검증에 실패했다. 원인은 미확정이며 원본을 보존했다. 처리량 개선율 비교에는 사용하지 않고 동일 조건을 한 차례 재측정했다. 다른 회차의 합계 90,001은 실행기에서 허용하는 도착 시점 경계 ±1건 안에 있다.

계수가 맞은 7회차 기존 → 5회차 후보 비교:

| 지표 | 기존 | 후보 | 변화 |
| --- | ---: | ---: | ---: |
| 최종 업무 성공 건수 | 67,120 | 73,301 | +9.2% |
| 미시작 요청 | 22,880 | 16,700 | −27.0% |
| 전체 p95 | 706ms | 665ms | −5.8% |
| 완료 API p95 | 700ms | 651ms | −7.0% |
| 오늘 조회 SQL 평균 | 0.579ms | 0.266ms | −54.1% |
| 평균 연결 획득 대기 | 67.73ms | 62.35ms | −7.9% |

이 비교는 조건별 한 회차다. 초기 캐시 영향은 실제 읽기 카운터로 줄였지만 호스트 상태, JIT, 쓰기 예열과 실행 순서의 영향까지 제거한 것은 아니다. 일반 예열 4회와 합쳐 하나의 평균 개선율로 표현하지 않는다.

## 조회 계획과 쓰기·저장 비용

기존 오늘 조회는 사용자 기준 인덱스로 103행을 가져와 3행을 필터링하고 정렬했다. 후보는 `(user_id, deleted_at, due_date)`로 3행을 직접 조회했고 별도 정렬이 사라졌다. 사전 보상 합계 조회는 기존의 과거 완료 100행 조회에서 후보의 당일 범위 조회로 바뀌었다. 사전에는 당일 완료가 없으므로 후보 범위의 실제 반환 행은 0이었다. 원본 `EXPLAIN ANALYZE`를 각 회차의 `index-plans.json`에 저장했다.

todo 인덱스의 `information_schema` 저장량은 186,613,760 → 334,790,656 bytes로 약 **141.3MiB 증가**했다. 기본 테이블 데이터는 224,165,888 bytes로 같았다. 전체 DB 파일·binlog·메모리 사용량과 혼동하지 않는다.

완료 API는 두 인덱스가 존재하는 상태에서 실제로 UPDATE·보상 원장·지갑·방 성장 트랜잭션을 수행했다. 일반 예열 비교에서는 완료 p95 개선이 없었고, 인덱스 예열 대조 한 쌍에서는 700 → 651ms로 줄었다. 이는 대기열을 포함한 API 지연이다. 인덱스 유지 자체의 순수 쓰기 비용이 줄었거나 0이라는 뜻은 아니다.

참고로 일반 예열 회차의 완료 상태 UPDATE 사후 누적 SQL 평균은 기존 약 0.24–0.27ms, 후보 약 0.38–0.39ms였다. 이 digest는 사전 상위 30개 목록에 없으므로 전후 차이를 0에서 시작한 것처럼 계산하지 않았다. 추가 인덱스의 쓰기 비용을 해석할 보조 관측으로만 남긴다.

성공 건수는 30초 도착 구간에서 시작한 요청의 최종 응답까지 포함한다. 이 수를 단순히 30으로 나눈 값을 지속 가능한 처리량이라고 표현하지 않는다. 서버 카운터는 Actuator의 처리 완료 수이며 ingress 측정이 아니다.

## 남은 병목과 다음 실험

인덱스 예열 후에도 DB는 부하 중 표본에서 약 2 CPU 제한 부근이었고 Hikari 대기자는 약 176–179명으로 남았다. 요청당 DB 명령 수는 관측·세션 설정·COMMIT 등을 포함해 약 10.5개였다. 평균 연결 획득 대기도 후보에서 62ms 이상이었다.

다음은 연결을 점유하는 동안의 SQL·JDBC 왕복·COMMIT 비용과 사용자별 첫 일일 활동 기록의 추가 트랜잭션을 분리 측정할 차례다. 이번 결과는 누적 이력용 인덱스의 필요성을 뒷받침하지만, 연결 풀을 계속 늘리거나 인덱스만으로 3,000 RPS를 통과한다고 판단할 근거는 아니다.

관리 지표는 회차당 5개 표본으로 성긴 편이며 조회 자체의 비용도 있다. 기존 verifier의 발생기 CPU 경고를 원문 그대로 보존했다. `ps`의 100%는 약 한 코어이므로 해당 경고만으로 발생기 전체 CPU 포화를 확정하지 않는다. 단일 맥북의 짧은 합성 부하로, 운영 네트워크·분산 처리·장시간 안정성을 검증한 것은 아니다.

## 재현과 검증

```bash
SCALE_API_CPUS=4 SCALE_DB_POOL=20 python3 qa/scale/run-local.py mixed \
  --rate 3000 --duration 30 --users 20000 --todos 60000 --vus 1000 --warmup 60 \
  --history-per-user 100 --todo-indexes baseline --skip-build
```

후보 회차는 `--todo-indexes candidate`로 바꾼다. 추가 예열 대조는 **양쪽에** `--warm-todo-indexes`를 붙인다. 목표 미달 시 종료 코드 1은 검증 실패이므로 반복 실행 시 해당 결과를 보존하고 다음 회차를 별도로 실행한다.

사전 smoke는 `20260910T121721-e9687c-mixed`: 1,000명, 활성 6,000건, 과거 3,000건, 100 RPS × 30초. 요청 3,000건 모두 성공, 완료 600건과 보상 6,000개를 대조했고 용량·정합성 검증을 통과했다. 본 비교와 다른 조건이므로 처리량 비교에 섞지 않았다.

최종 Python QA 63개와 k6 응답 계약 검사 12개 통과. 실제 부하 검증은 위 결과대로 목표 미달이다. 애플리케이션 변경이 없어 Gradle 테스트는 다시 실행하지 않았다. 실험은 운영·개발 DB에 접속하지 않았으며, 모든 실험 컨테이너·볼륨·네트워크를 정리했다.
