# 조회 최적화: 응답 유지와 SQL 감소 검증

`/today`의 빈 루틴 로그 조회를 생략하고, 투두·완료 로그·온보딩 요약을 필요한 컬럼만 읽도록 바꿨다. 유효한 회차별 평균 성공 요청은 72,803 → 76,121건(+4.6%)이었다. 전체 p95 평균은 685.5 → 663.0ms(-3.3%)다. 3,000 RPS 목표에는 모든 회차가 미달했다.

이 변경으로 조회 낭비가 줄고 기존 응답이 유지되는 것은 확인했다. 조건별 두 번의 짧은 로컬 측정으로 안정적인 처리량 개선율이나 운영 용량을 확정하지 않는다. 포트폴리오에서는 이 변경을 병목 조사 중 하나의 실험으로 설명하며, 대규모 트래픽 문제를 해결한 단독 성과로 표현하지 않는다.

## 변경과 응답 계약

| 경로 | 기존 | 수정 |
| --- | --- | --- |
| `/today`, 오늘 대상 루틴 없음 | SELECT 4회 | 완료 로그 조회 생략, SELECT 3회 |
| `/today` 투두 조회 | 엔티티 17개 컬럼 | `TodoAgendaRow`의 7개 컬럼 |
| `/today` 완료 로그 조회 | 엔티티 9개 컬럼 | 루틴 ID 1개 컬럼 |
| `/today` 루틴 후보 | ACTIVE 전체 조회 후 기간 검사 | SQL에서 시작일·종료일 범위를 먼저 적용, 세부 반복 판정 유지 |
| `/me` 목표 조회 | 목표 상세 포함 10개 컬럼과 응답에 없는 DTO 목록 | 목표 ID·대표 여부 2개 컬럼 |
| `/me` 선택 캐릭터 조회 | 보유 엔티티 8개 컬럼 | 캐릭터 ID 1개 컬럼 |

`/me`의 업무 SELECT 횟수는 3회로 같다. 온보딩 완료는 대표 목표 유무와 무관하게 목표 존재와 선택 캐릭터 존재로 판정하며, 목표 정렬에 따른 대표 선택·삭제된 보유 캐릭터 제외 조건을 유지했다. 전체 온보딩 상세 API의 목표 코드·이름 목록은 유지했다.

`DailyAgendaAssembler`가 읽기 행을 받도록 변경했고, 기존 달력 경로는 조회한 투두를 같은 행으로 변환해서 조립한다. 달력의 DB 조회 범위나 과거 판정 규칙은 바꾸지 않았다. 응답 필드·카테고리 그룹·정렬·완료 및 진행률·스트릭과 소유권 필터를 유지했다. 투두 완료의 잠금·보상·중간 flush 및 방 upsert는 이번 변경에 포함하지 않았다. QueryDSL 의존성과 Flyway migration은 추가하지 않았다.

## 검증

- `./gradlew --no-daemon test :user-api:bootJar`: 총 1,996건, 실패 0, 오류 0. 1,995건 통과, 외부 AI를 호출하는 기존 live smoke 1건 제외.
- 오늘 조회의 기간 경계·기간 밖/삭제/다른 사용자 제외, 미분류/삭제 카테고리 유지, 투두 완료 시각·정렬·요약, 빈 루틴의 SQL 횟수를 검증했다.
- 온보딩 요약의 목표/캐릭터/대표 유무 조합을 상세 응답과 비교하고, 요약 조회에서 엔티티를 로딩하지 않음을 확인했다.
- 기존 JAR와 수정 JAR의 실제 MySQL HTTP 8개 응답을 대조했다. 실행 때마다 달라지는 POST 완료 시각을 제외하면 모든 응답과 HTTP status가 같았다. 조회 응답은 모든 필드를 그대로 비교했다.
- 단건 완료 사용자별 투두 보상·성장 보상·지갑·원장·방 포인트가 모두 10으로 일치했다. 기존 방/방이 없는 경우 모두 성공했다.
- QA Python 테스트 56건과 인덱스 보조 테스트 9건 통과. `git diff --check` 통과.

## 동일 조건 부하 비교

사용자 20,000명, 오늘 투두 60,000건, 과거 무보상 완료 투두 2,000,000건이다. 읽기 80%(`/me`, `/today`), 투두 완료 20%를 3,000 RPS로 30초간 계획했다. 매 회차 새 MySQL DB를 만들었다. API 4 CPU/2 GiB/heap 1 GiB, DB 2 CPU/2 GiB/buffer pool 1 GiB, Hikari 20으로 고정했다. 읽기 100 RPS 60초와 모든 투두 인덱스의 순차 읽기로 예열했다.

앞서 실험한 `(user_id, deleted_at, due_date)` 및 `(user_id, status, completed_at)` 후보 인덱스를 **양쪽에 동일하게** 적용했다. 따라서 이 결과를 기존 인덱스 환경과 비교한 인덱스 개선율에 합산하지 않는다. durability는 flush-at-commit=1, sync-binlog=1, binlog ON이다.

| 회차 | 코드 | 성공 요청 | 미시작 | 전체 p95 | 완료 p95 | 평균 연결 획득 대기 | 요청 계수 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 기존 | 75,865 | 14,137 | 644.0ms | 619.0ms | 60.31ms | 실패·평균 제외 |
| 2 | 수정 | 75,565 | 14,436 | 683.0ms | 668.0ms | 51.48ms | 통과 |
| 3 | 수정 | 76,677 | 13,323 | 643.0ms | 636.3ms | 32.58ms | 통과 |
| 4 | 기존 | 74,071 | 15,930 | 677.0ms | 664.0ms | 61.78ms | 통과 |
| 5 | 기존 | 71,535 | 18,466 | 694.0ms | 689.0ms | 63.65ms | 통과 |

유효 회차별 평균 연결 획득 대기는 62.71 → 42.03ms(-33.0%)였다. Hikari acquire 타이머의 부하 전후 COUNT/TOTAL_TIME 차이로 계산했다. 이는 연결을 빌리기까지의 대기이며 연결 점유 시간은 아니다. p95 평균은 회차별 p95의 산술 평균으로, 전체 요청을 합친 백분위가 아니다.

기존→수정→수정→기존을 계획했지만 첫 기존 회차의 발송+미시작 합계가 90,002건으로 목표 90,000건 대비 ±1건 기준을 넘었다. 해당 회차는 보존하되 평균에서 제외하고 기존 버전을 재측정했다. 유효 회차만 남기면 실행 순서는 수정→수정→기존→기존이므로 시간·예열·호스트 상태의 영향을 완전히 상쇄한 비교가 아니다. 요청 계수 차이의 원인은 확정하지 않았다. 기준을 완화하거나 실패를 성공으로 바꾸지 않았다.

모든 회차에서 발송=업무 성공=API별 서버 처리 완료 합계가 일치했고, 실행된 완료 요청의 사용자별 보상/원장/방 성장 및 과거 200만 건 불변 검사를 통과했다. 모든 부하 구간의 버퍼풀 미스 읽기 증분은 0이었다. 미시작 요청과 지연 기준 때문에 용량 판정은 모두 `capacity_failed`다. 실행 요청의 정합성 통과를 3,000 RPS 통과로 해석하지 않는다.

이 혼합 부하에는 루틴과 선택 목표 데이터가 없다. 빈 루틴 로그 생략과 투두 projection은 포함되지만, 기간 외 루틴이나 목표 상세 로딩 감소 효과는 단건 SQL/회귀 테스트에서 확인한 범위다. 실제 사용자 분포·장시간 운용·네트워크 지연·운영 배포는 검증하지 않았다.
