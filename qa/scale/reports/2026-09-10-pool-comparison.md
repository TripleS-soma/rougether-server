# DB 연결 풀 10 → 20 비교

VU 1,000 조건의 탐색 비교에서 pool을 20개로 늘리자 업무 성공 요청이 31.3% 증가했고, 전체 요청 p95는 29.6%, 평균 연결 획득 대기는 49.2% 줄었습니다. 다만 두 조건 모두 3,000 RPS 유입과 p95 300ms 기준에 미달했습니다. 각 조건 1회 비교이므로 개선 폭의 재현성과 최적 pool 크기를 확정하지 않습니다.

## 비교 조건

- API 4 CPU / 2GiB / heap 1GiB, MySQL 2 CPU / 2GiB / buffer pool 1GiB.
- 사용자 20,000명, 투두 60,000건. 읽기 80%, 완료 20%.
- 100 RPS 읽기 예열 60초 후, 3,000 RPS 목표로 30초 실행. 계획 요청은 90,000건.
- 아래 비교는 preallocated/max VU를 모두 1,000으로 고정. 변경한 서버 설정은 `SCALE_DB_POOL=10` 또는 `20`.
- DB 스냅샷 연결 수는 측정용 연결 1개를 포함해 각각 11개와 21개.
- `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, binlog ON 유지.
- 기존 실험과 동일 JAR SHA-256: `f397889a244376d67ee396922013ca49635b0582212f13551c4223d61c482dec`.

| 발송 요청의 업무 성공률 | 100% | 100% | |
| 관측된 투두 완료 / 코인 | 11,510 / 115,100 | 15,112 / 151,120 | |

pool 10: `20260910T113808-a1c029-mixed`.
pool 20: `20260910T114024-816515-mixed`.

성공 요청 수는 30초 부하 동안 시작한 요청의 최종 업무 성공 건수입니다. 미시작 요청은 k6가 실행 슬롯을 얻지 못한 `dropped_iterations`입니다. 발송+미시작이 계획보다 1건 많은 것은 도착 시점 경계의 허용 오차입니다. 평균 연결 대기는 요청당 평균이 아니라 Hikari acquisition COUNT와 TOTAL_TIME의 전후 차이로 계산했습니다.

두 회차 모두 클라이언트 발송 수, 업무 성공 수, API별 서버 처리 완료 카운터 합계가 일치했습니다. 전송 오류 로그는 0건입니다. 소유권 불일치, 중복 원장, 원장 소유자 뒤바뀜은 모두 0건입니다. 그러나 미시작 요청 때문에 계획 전체와의 완료/보상 대조 값은 미확정(null)이며, DB 감사와 용량 판정을 통과시키지 않았습니다.

## VU 5,000의 전체 실행 기록

기존 조건을 먼저 반복했으나 pool 10과 20 양쪽에서 대량 TCP reset/EOF/timeout이 발생한 회차가 있었습니다. 이후 양쪽의 동시 실행 슬롯을 1,000개로 낮춰 별도 조건으로 비교했습니다. 5,000 → 1,000 변경의 효과를 pool 증가의 효과에 섞지 않습니다. 아래 실패 회차도 모두 보존합니다.

| 실행 순서 / run ID | pool | 발송 | 업무 성공 | 미시작 | 전체 p95 | 전송 오류 로그 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 · `20260910T112615-7de43c-mixed` | 20 | 89,998 | 80 | 3 | 5,000ms | 89,918 |
| 2 · `20260910T112922-11e8b9-mixed` | 10 | 67,574 | 67,485 | 22,427 | 3,300ms | 89 |
| 3 · `20260910T113156-47c9eb-mixed` | 20 | 77,084 | 76,955 | 12,916 | 3,161ms | 129 |
| 4 · `20260910T113435-53ff51-mixed` | 10 | 77,109 | 9,775 | 12,892 | 5,000ms | 67,334 |

1·4회차는 사후 관리 API도 응답하지 않아 서버 완료 카운터와 Hikari 누적 대기 시간의 전후 비교를 얻지 못했습니다. DB 최종 스냅샷은 API 정지 후 수집했습니다. 1회차는 클라이언트 완료 성공 응답 0건과 DB 완료 623건이 달랐습니다. 이를 풀 증설 효과나 재화 손상으로 단정하지 않습니다. 전송 오류 자체의 근본 원인도 아직 미확정입니다.

2·3회차는 업무 성공이 67,485 → 76,955건으로 늘었지만 전송 오류가 남았습니다. 개선된 한 쌍만 선택해 반복 실험이 모두 성공했다고 표현할 수 없습니다. 2회차에는 별도 health 요청 2건도 확인용으로 실행했습니다. 3회차 종료 후 health 확인은 컨테이너 정리 뒤였으므로 부하 중 장애 진단 근거에서 제외합니다.

## 해석과 남은 범위

20개는 후속 로컬 실험의 후보로 삼을 근거가 있습니다. 연결 대기와 요청 대기열이 줄었지만, DB CPU는 두 조건의 부하 중 표본에서 2코어 제한 부근이었고 pool 20에서도 pending이 남았습니다. 풀 크기를 계속 늘리면 같은 비율로 처리량이 증가한다고 주장하지 않습니다.

관측은 각 VU 1,000 회차에서 5개 표본뿐입니다. 기존 verifier는 발생기의 ps CPU 90% 초과를 경고하지만, ps 100%는 약 한 코어 사용량이므로 이 경고만으로 전체 발생기 CPU 포화를 확정하지 않습니다. 모든 회차의 verifier 원본과 경고를 증거 JSON에 그대로 보존했습니다.

같은 맥북에서 발생기·API·DB를 실행했고, 호스트 상태와 실행 순서를 완전히 통제하지 못했습니다. 읽기 예열만 했으므로 모든 사용자 키와 쓰기 경로가 충분히 예열됐다고 보장하지 않습니다. 서버 완료 수는 Actuator 완료 카운터이며 ingress timestamp가 아닙니다.

운영 설정과 애플리케이션 코드는 변경하지 않았습니다. 격리 실험의 환경 변수로만 pool 20을 적용했습니다. 목표 유입 누락 0건, API별 p95 ≤ 300ms / p99 ≤ 1초, 업무 성공률과 최종 DB 대조를 모두 만족하는 3,000 RPS 용량은 아직 검증되지 않았습니다.

## 재현과 검증

```bash
for pool in 10 20; do
  SCALE_API_CPUS=4 SCALE_API_MEMORY=2g SCALE_API_HEAP=1024m \
  SCALE_DB_CPUS=2 SCALE_DB_MEMORY=2g SCALE_DB_POOL="$pool" \
  SCALE_DB_BUFFER_BYTES=1073741824 \
  bash qa/scale/run-local.sh mixed --rate 3000 --duration 30 \
    --users 20000 --todos 60000 --vus 1000 --warmup 60 --skip-build
done
```

목표 미달 회차의 종료 코드 1은 예상된 검증 실패입니다. `set -e` 환경에서 반복문 전체가 중단되지 않도록 각 종료 코드를 기록하며 실행해야 합니다. 기존 JAR가 필요합니다.

6회 모두 실험 소유 컨테이너·볼륨·네트워크 정리 완료가 기록됐습니다. 같은 JAR, 실행 도구/시나리오 hash, 컨테이너 이미지·CPU·메모리 조건 및 요청 합계를 대조했습니다. 애플리케이션 코드 변경이 없어 Gradle 테스트를 다시 실행하지 않았습니다.
