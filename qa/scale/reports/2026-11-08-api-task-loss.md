# API 두 대 중 한 대를 중단했을 때

2026년 11월 8일, 격리 ECS의 사용자 API 두 대가 요청을 받고 있을 때 한 대를 중단했다. **교체 태스크가 ALB에서 정상으로 보이기까지 99.82초**가 걸렸다. 그 사이 들어온 HTTP 요청 5,989건에서 예상 밖 오류는 0건이었다. 정상 대상이 한 대뿐이었던 구간의 p99는 26.05ms였다.

## 무엇을 실행했나

- API는 Fargate 두 대, 각각 4 vCPU, 8 GiB, DB 풀 20개였다. 같은 테스트 RDS `db.t4g.medium`에 전용 스키마를 만들었다. ALB 대상 그룹은 라운드 로빈, 등록 해제 대기 30초, `/actuator/health` 확인 주기 15초였다.
- 초당 50개의 최초 요청을 보냈다. 다섯 건 중 네 건은 내 정보 또는 오늘 일정 조회, 한 건은 투두 완료였다. 완료 요청마다 같은 투두 ID로 한 번 더 POST해서 실제 HTTP 요청은 약 60건/초였다. 자동 전송 재시도는 껐다.
- ALB에서 두 대상이 모두 healthy이고 세 종류의 API 응답과 중복 완료 응답이 계약을 만족하는지 확인했다. 그 뒤 살아 있는 태스크 하나를 골라 ECS `StopTask`를 호출했다. 교체 태스크가 healthy가 된 뒤에도 20초 이상 트래픽을 유지했다.

## 요청은 계속 처리됐나

| HTTP 요청이 시작된 구간 | 요청 수 | 예상한 중복 409 | 예상 밖 오류 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 중단 지시 전 | 1,532 | 255 | 0 | 30.21ms | 224.44ms |
| 중단 지시부터 교체 태스크 healthy까지 | 5,989 | 998 | 0 | 24.16ms | 32.86ms |
| 교체 태스크 healthy 이후 | 1,319 | 220 | 0 | 29.70ms | 74.08ms |
| 전체 | 8,840 | 1,473 | 0 | 26.13ms | 39.95ms |

중단 지시는 12:53:29 KST였다. 아래 시각은 이때부터의 경과 시간이다. ALB와 ECS 상태는 API를 폴링해서 처음 확인한 시각을 썼다.

| 경과 | 관측 |
| ---: | --- |
| 0.05초 | ECS가 중단 요청에 응답했다. |
| 40.93초 | ALB에서 기존 대상이 draining 상태로 바뀌었다. 정상 대상 한 대가 남았다. |
| 71.62초 | 기존 대상이 ALB 등록 목록에서 사라졌다. |
| 88.06초 | 교체 태스크가 RUNNING으로 관측됐다. |
| 99.82초 | 교체 태스크가 ALB에서 healthy가 되어 정상 대상이 두 대로 돌아왔다. |

정상 대상이 한 대인 **58.89초** 동안 요청 3,533건이 시작됐다. 2,355건은 조회 성공, 589건은 완료 성공, 589건은 의도한 중복 거절이었다. 전송 실패와 HTTP 5xx는 없었다. 본부하 전체에서 연속한 최초 요청 사이의 최대 간격은 43.83ms였다.

## 완료와 보상은 한 번씩 반영됐나

서로 다른 투두 1,473개를 완료했다. 최초 호출 1,473건은 모두 `201`, 같은 ID로 보낸 재시도 1,473건은 모두 `409 TODO_ALREADY_COMPLETED`였다. DB에서 1,473개 각각에 대해 완료 상태, 보상 원장 한 행, 소유자, 코인 잔액 10, 방 성장치 10을 확인했다. 실험 범위 밖에 기록된 추가 보상은 0건이었다.

이번 회차에서는 최초 완료 응답이 실제로 유실된 사례가 없었다. 검증한 범위는 **정상적인 ECS 중단 중 서비스 연속성과 같은 완료 요청을 다시 보냈을 때의 정합성**이다. 1,000 RPS에서의 장애 허용량, 프로세스 강제 종료, DB 장애 조치는 별도 조건이다.

## RPS, TPS, QPS

| 지표 | 계산 | 결과 |
| --- | --- | ---: |
| HTTP RPS | 최초 요청과 재시도를 포함한 8,840건 ÷ 147.335초 | 60.00 |
| 투두 완료 TPS | DB에서 완료와 보상을 확인한 서로 다른 투두 1,473개 ÷ 147.335초 | 10.00 |
| DB QPS | MySQL 전역 Questions 증가분 (118,693 − 49,733) ÷ 147.335초 | 468.05 |

DB QPS에는 모니터링을 포함해 해당 MySQL 인스턴스가 처리한 클라이언트 명령이 들어간다. 로컬 k6에서도 같은 계산을 확인했다. 목표 20 RPS인 별도 회차에서 20.460초 동안 2,904 증가해 141.93 QPS였고 HTTP 판정과 DB 감사가 통과했다. QPS 표본을 남기지 않은 과거 1,500 RPS 회차는 미수집 상태다.

첫 AWS 시도에서는 실험기가 정상적인 투두 완료 응답 `201`을 실패로 판정해 중단 지시 전에 종료했다. 이 회차를 원복하고 검증기를 고친 뒤 재실행했다. 위 표는 재실행 결과다.

원복 후 격리 서비스는 원래 태스크 정의로 desired 1, running 1, ALB healthy 1이었다. RDS는 `db.t4g.medium` available, 변경 대기 없음이었다. 실험 스키마 삭제, 발생기 종료, 임시 태스크 정의 비활성화, S3 실험 파일과 임시 ECR 태그 삭제를 확인했다. QA 테스트 60개를 통과했다.
