# 투두 완료 실험: 방 존재 확인을 추가한 후보는 미채택

**판정: 이 보고서의 조합 후보는 채택하지 않았다. 평균 처리량 -5.6%, p95 +8.8%로 성능 이득을 입증하지 못해 방 존재 확인 분기를 되돌렸다. 투두 UPDATE만 합치는 별도 후보를 후속 검증한다.**

이 실험에서는 투두 완료의 성장 보상 기록을 방 성장 처리 앞으로 옮기고, 방이 없을 때만 생성 보장 upsert를 실행했다. 완료 상태·지갑·원장·방 성장의 트랜잭션 경계와 사용자→지갑→방 잠금 순서는 유지했다. 운영 배포나 DB 스키마 변경은 하지 않았다.

같은 조건의 유효 회차별 평균 업무 성공은 75,602 → 71,388건(-5.6%), 전체 p95 평균은 674.5 → 734.0ms(+8.8%)다. 이 수치는 각 버전 두 번의 30초 로컬 측정이며 운영 처리량이나 안정적인 개선율로 확정하지 않는다.

## 실제 SQL과 변경 이유

보상 10을 지급하는 단건 HTTP 완료의 결과다. SELECT에는 사용자·지갑·방 잠금 조회와 일일 보상 합계가 포함된다. INSERT 계열에는 원장 INSERT와 방 upsert를 세며, upsert의 ON DUPLICATE KEY UPDATE를 UPDATE에 중복 집계하지 않는다.

| 조건 | 코드 | SELECT | INSERT 계열 | UPDATE 전체 | 그중 투두 UPDATE | 방 생성 보장 upsert |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 기존 방 | 기존 | 6 | 2 | 4 | 2 | 1 |
| 기존 방 | 수정 | 7 | 1 | 3 | 1 | 0 |
| 방 없음 | 기존 | 6 | 2 | 4 | 2 | 1 |
| 방 없음 | 수정 | 7 | 2 | 3 | 1 | 1 |

기존 방에서는 쓰기 SQL이 6→4회로 줄고 존재 확인 SELECT가 1회 추가되어 업무 SQL 총수는 12→11회다. 방이 없으면 첫 생성 upsert를 유지하므로 총수는 12회로 같지만 투두 UPDATE는 2→1회다. SQL 횟수 감소를 디스크 쓰기나 지연의 동일한 비율 감소로 해석하지 않는다.

`TodoService.complete()`는 `recordGrowthReward()`를 `RoomGrowthService.award()`보다 먼저 호출한다. 생성 보장의 중간 flush가 실행되더라도 투두 완료 상태와 성장 보상을 함께 저장한다. 성장 지급이 실패하면 앞서 기록한 값도 같은 트랜잭션에서 롤백된다.

`RoomGrowthService.award()`는 비잠금 `existsById()`가 false일 때만 기존 `ensureExists()`를 호출한다. 존재 확인은 분기용이며 방의 변경 권한을 대신하지 않는다. 실제 성장 반영은 기존 `findWithLockById()`로 잠근 행을 사용한다. 존재 확인 사이에 다른 경로에서 방을 만들더라도 upsert가 기존 성장·배치를 덮어쓰지 않는다.

없는 방을 먼저 SELECT FOR UPDATE한 뒤 INSERT하는 방식은 사용하지 않았다. REPEATABLE READ에서 서로 다른 사용자의 첫 방 생성이 같은 인덱스 간격 잠금을 선점한 뒤 INSERT를 기다리는 경합을 피하기 위해, 비잠금 존재 확인과 기존 upsert 생성 경로를 유지했다. 공용 저장소의 `flushAutomatically=true`도 유지해 신규 회원 FK flush 동작을 바꾸지 않았다.

공유 성장 서비스의 변경은 루틴 보상 경로에도 적용되므로 루틴·투두의 혼합 완료, 부분 지급, 취소, 모루 보상, 방 배치 동시 저장까지 전체 회귀 검증에 포함했다. 루틴 집계/일일 합계 캐시/DB CPU/풀/QueryDSL은 이번 변경 범위에 넣지 않았다.

## 동일 조건 부하 비교

실제 JWT 인증, `/me` 40% + `/today` 40% + 투두 완료 20%, 3,000 RPS × 30초 = 계획 90,000건. 사용자 20,000명, 오늘 투두 60,000건, 과거 무보상 완료 2,000,000건, 고정 VU 1,000이다. 매 회차 새로운 영속 MySQL 8.4 DB를 사용했다.

API 4 CPU/2 GiB/heap 1 GiB, DB 2 CPU/2 GiB/buffer pool 1 GiB, Hikari 20을 고정했다. Docker Desktop VM 12 CPU/약 7.7 GiB이며 호스트의 다른 앱과 자원을 공유한다. 양쪽 모두 이전 조회 최적화 및 동일한 후보 인덱스 두 개를 포함한다. 인덱스 전수 읽기와 읽기 100 RPS × 60초로 예열했다. durability는 flush-at-commit=1, sync-binlog=1, binlog ON이다.

| 회차 | 코드 | 업무 성공 | 미시작 | 전체 p95 | 완료 p95 | 연결 획득 대기 평균 | 연결 점유 평균 | 요청 계수 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 기존 | 77,878 | 12,123 | 621.0ms | 612.0ms | 29.15ms | 4.88ms | 통과 |
| 2 | 수정 | 76,941 | 13,060 | 656.0ms | 638.0ms | 42.19ms | 5.58ms | 통과 |
| 3 | 수정 | 65,834 | 24,167 | 812.0ms | 795.0ms | 65.69ms | 7.03ms | 통과 |
| 4 | 기존 | 73,326 | 16,675 | 728.0ms | 719.0ms | 49.70ms | 6.01ms | 통과 |

평균 연결 획득 대기는 39.43→53.94ms, 연결 점유는 5.44→6.30ms였다. Hikari acquire/usage 타이머의 부하 전후 TOTAL_TIME 차이를 COUNT 차이로 나눈 값이다. 모든 엔드포인트의 연결 사용 한 번당 평균이며, 투두 완료 트랜잭션만의 점유 시간은 아니다. p95 평균도 전체 요청을 합친 백분위가 아닌 회차별 p95의 산술 평균이다.

모든 회차에서 발송=업무 성공=서버 엔드포인트 처리 완료 합계, 실행된 완료 요청의 사용자별 지갑·원장·방 성장 일치 및 과거 이력 불변을 확인했다. 목표 요청 계수와 용량 판정은 별도로 유지한다. 각 회차의 미시작·지연·판정과 원본 hash는 JSON에 보존한다.

실험은 기존→수정→수정→기존 순서로 계획했다. 유효 요청 계수 기준은 발송+미시작−90,000의 절댓값 ≤1이며, 이 기준을 넘는 회차는 삭제하거나 성공 처리하지 않고 평균에서 제외한다. 예열/JIT/호스트 변동을 완전히 통제한 장시간 실험은 아니다.

부하 fixture는 방이 이미 있는 사용자와 투두 완료 중심이다. 첫 방 생성, 동시 완료/취소, 루틴·모루 경로는 기능/SQL 검증 범위이며 이 부하 수치로 해당 경로의 성능을 주장하지 않는다. 서버 여러 대·AWS·운영 배포는 검증하지 않았다.

발생기 CPU에 대한 검증기 경고도 회차별 JSON의 measurement_limits에 보존했다. ps의 프로세스 CPU 백분율이 100을 넘는 것은 멀티코어 프로세스에서 가능하므로, 이 경고만으로 발생기 전체 용량이나 단일 병목을 확정하지 않는다. 호스트 공유·발생기 여유·예열 편차를 포함한 측정 한계다.
